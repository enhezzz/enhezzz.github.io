Agent Skill 完全指南：从触发机制到自定义开发
发表于 2026-09-18| 更新于 2026-09-18|AI
字数总计: 8.3k|阅读时长: 31 分钟

给 Agent 分配任务，每次都要解释一遍”怎么做”：部署要先检查环境变量、跑测试、打 tag，代码审查要看命名、看边界、看测试覆盖……重复一百遍，Agent 还是得靠上下文记住。Skill（技能）要解决的就是这个”每次都要教一遍”的问题：把团队/项目的标准操作流程打包成可复用的指令集，让 Agent 一次学会、每次都对。

本文按这个顺序展开：Agent 和 Skill 到底是什么关系、Skill 在什么时刻被触发、Skill 里装了哪些东西、怎么创建自己的 Skill、有哪些注意要点，最后梳理整个执行流程。

一、先把关系理清楚：Skill 不是工具，是”工作记忆”

最常见的误解是把 Skill 当成”函数”或”工具”。它不是。Skill 是一套打包好的指令，告诉 Agent “遇到这类任务该怎么做”。

三个概念必须分清：

概念 是什么 类比
Agent（代理） 执行任务的 AI 实体，持有上下文、调用工具 一个有经验的工程师
Tool（工具） Agent 调用的原子能力，如读文件、跑命令 工程师手里的 Git、Docker、IDE
Skill（技能） 针对特定任务的操作指南，教 Agent “怎么做好” 工程师脑子里的”部署 SOP”

Skill 完全不参与”执行”。它不会自己读文件、跑命令、改代码——这些都是 Tools 干的事。Skill 只是一份”剧本”，告诉 Agent：

  • 遇到这个任务，先做什么、再做什么
  • 哪些地方容易出错
  • 什么情况要停下来问用户

这也是为什么同一个 Skill 可以被多个 Agent 使用、可以在不同项目间复用——它只是知识，不包含状态。

二、Skill 在什么时候被触发

这是理解 Skill 的关键：触发方式决定了 Skill 的设计。

触发时机有两种

显式调用：斜杠命令

这是最可控的方式。用户清楚自己在调用什么，Agent 也不会误判。

隐式匹配：自然语言

隐式匹配的关键是 Skill 的 description 必须写得足够具体，要包含能让 Agent 识别的关键词。

什么时候不会触发 Skill

即使有 Skill，以下情况也不会自动触发：

  1. 任务太简单：”读一下 README” → 直接 Read，不需要 Skill
  2. 没有匹配的 Skill：”帮我写个 Python 爬虫” → 项目里没有 web-scraping skill
  3. Skill 描述不匹配：用户说”上线”，但 Skill 描述里只写了”deploy”
  4. 已经在 Skill 内部：Skill 执行过程中不会再次触发自己（防止递归）

四、如何创建自己的 Skill

步骤 1：确定 Skill 的范围

先问自己三个问题：

  1. 这是一个重复性任务吗？

    • 是 → 适合做成 Skill
    • 不是 → 可能只是一次性脚本

  2. 这个任务有标准流程吗？

    • 有 → 适合做成 Skill
    • 没有，每次都不同 → 不适合

  3. 这个任务需要人工判断吗？

    • 需要一些判断 → 在 Skill 里加确认点
    • 完全自动化 → 考虑做成工具或脚本
    • 完全靠人 → 不适合做成 Skill

适合做成 Skill 的任务：

  • ✅ 部署流程（有标准步骤，但需要人确认关键节点）
  • ✅ 代码审查清单（重复性高，但需要人判断）
  • ✅ 数据库迁移（标准流程，高风险需要确认）
  • ✅ 创建新组件（有脚手架模板，但可能需要调整）

不适合做成 Skill 的任务：

  • ❌ 修复特定 bug（一次性任务）
  • ❌ 探索性数据分析（每次都不同）
  • ❌ 紧急故障处理（太依赖上下文）

1. Description 是成败的关键

好的 description 特征：

  • ✅ 包含用户可能用的同义词（部署 / 上线 / 发布 / 推送）
  • ✅ 说明具体做什么（”包括构建、上传、验证”）
  • ✅ 指明适用范围（”前端应用” vs “后端服务”）

坏的 description 特征：

  • ❌ 太简单（”部署”）
  • ❌ 太宽泛（”处理代码相关的事”）
  • ❌ 没有关键词（”Skill 1”）

Skill 在 Agent 上下文中的位置

关键点：

  • Skill 不是”函数调用”，而是临时加载到上下文的”指导手册”
  • Agent 按照 Skill 的指令一步步执行，就像在遵循一份 SOP
  • 执行过程中 Agent 仍然可以调用所有 Tools
  • Skill 执行完成后，内容会从上下文中移除（节省 token）

八、实战案例：一个完整的代码审查 Skill

让我们通过一个真实的例子，把前面的所有知识点串起来。

场景

前端团队要求所有 PR 合并前必须经过统一的代码审查，包括：

  • 代码规范检查
  • 边界条件处理
  • 性能考虑
  • 可访问性（a11y）
  • 测试覆盖

code-review.skill.md

  • null/undefined 的处理
  • 异步操作的 loading/error 状态

3.3 性能考虑

  • 是否有不必要的重复渲染
    • React：是否缺少 useMemo/useCallback
    • Vue：是否正确使用 computed
  • 大列表是否做了虚拟滚动
  • 图片是否懒加载

3.4 可访问性（a11y）

  • 按钮是否有 aria-label
  • 图片是否有 alt
  • 表单是否有 label
  • 键盘导航是否可用（tabIndex）

3.5 安全性

  • 用户输入是否转义（防 XSS）
  • API 调用是否有鉴权
  • 敏感信息是否暴露在前端

3.6 错误处理

  • try-catch 包裹异步操作
  • 错误信息是否友好（用户能懂）
  • 是否有错误上报（Sentry 等）

步骤 4：测试覆盖检查

```bash
npm run test:coverage –
```

评估标准：

  • 覆盖率 ≥ 80%：✓ 通过
  • 覆盖率 60-80%：⚠️ 建议补充
  • 覆盖率 < 60%：❌ 要求补充测试

注意事项

审查原则

  1. 不是找茬，是帮助

    • 指出问题的同时给出建议
    • 肯定做得好的地方

  2. 区分严重程度

    • Critical：必须修复（安全、功能缺陷）
    • Warning：应该修复（性能、可维护性）
    • Suggestion：锦上添花（风格、优化）

  3. 提供示例代码

    • 不要只说”这里有问题”
    • 给出”应该怎么改”的代码示例

常见陷阱

  • ⚠️ 不要因为一个小问题就拒绝整个 PR
  • ⚠️ 不要过度关注代码风格（那是 linter 的工作）
  • ⚠️ 不要忽略测试覆盖（这是质量保证的底线）

技术栈特定注意事项

React：

  • 检查 Hooks 依赖数组是否正确
  • 检查是否有不必要的 re-render

Vue：

  • 检查 ref 和 reactive 的使用是否合理
  • 检查 watch 是否需要 deep 选项

TypeScript：

  • 检查是否有 any 类型（应该用具体类型）
  • 检查是否有未处理的 Promise

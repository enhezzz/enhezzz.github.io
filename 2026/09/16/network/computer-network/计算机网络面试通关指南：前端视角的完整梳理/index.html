计算机网络面试通关指南：前端视角的完整梳理
发表于 2026-09-16| 更新于 2026-09-16|Network
字数总计: 20.7k|阅读时长: 77 分钟

前端面试里的计算机网络有个特点：问题看起来很基础，但答案的深度决定了面试官对你的判断。”三次握手为什么是三次”能答一句”确认双方收发能力”，也能从”防止历史连接初始化”讲到 TCP 状态机；”强缓存和协商缓存的区别”能背出两个响应头，也能画出完整决策树并说清 no-cache 和 no-store 到底差在哪。

本文按数据在网络中流动的顺序展开：从 DNS 解析到 TCP 建连、从 TLS 握手到 HTTP 报文、从缓存策略到 HTTP/2 与 HTTP/3、从同源策略到 WebSocket。每个知识点都配图说明机制，并标注面试中真正会被追问的地方。所有内容以前端工程师需要的深度为准——不纠缠路由算法的数学证明，但要能解释清楚一个请求慢在哪里。

一、分层模型与一次请求的全景

1.1 为什么要分层

网络协议栈分层的核心动机是解耦：每一层只需要关心自己的职责，向上提供服务、向下依赖服务，层内实现可以整体替换而不影响其他层。这也是为什么 HTTP/3 能把传输层从 TCP 换成 QUIC，而应用层的语义几乎不变。

OSI 七层是教学模型，实际工程中用的是 TCP/IP 四层。面试问”OSI 分层”时，答出对应关系比背诵七个名字更有价值：

面试高频追问：IP 地址和 MAC 地址为什么都需要？ IP 是逻辑地址，用于跨网段路由（”从北京到上海”）；MAC 是物理地址，用于同一链路内的下一跳投递（”从这个路口到下一个路口”）。整条路径上 IP 头的源/目的 IP 基本不变，而每经过一个路由器，链路层的 MAC 地址就要重写一次。

2.2 缓存层级与常见记录类型

一次 DNS 查询可能在任何一层命中，这决定了 DNS 耗时可能是 0ms 也可能是 200ms+：

层级 生效范围 前端可控性
浏览器 DNS 缓存 单个浏览器进程 不可控，Chrome 约 60s
操作系统缓存 / hosts 整台机器 开发时可改 hosts
路由器缓存 局域网 不可控
本地 DNS（运营商 / 公共 DNS） 该 DNS 的所有用户 不可控，受 TTL 影响
权威 DNS 全局 可通过设置 TTL 控制生效速度

常见记录类型：

面试追问：CNAME 和 A 记录该用哪个？ 接 CDN 必须用 CNAME，因为 CDN 需要根据用户地理位置动态返回不同的边缘节点 IP，写死 A 记录就失去了调度能力。但根域名（example.com，即 zone apex）在 DNS 规范里不能配 CNAME，需要用厂商提供的 ALIAS / ANAME 记录，或者做 301 跳到 www 子域。

DNS 解析是关键路径的第一步，且完全串行——不解析完就没法建连。三个资源提示（Resource Hints）的区别是高频考点：

实践要点：

  • preconnect 不要超过 4~6 个域名，每条连接都占用资源，滥用反而拖慢首屏。
  • 加载跨域字体时 preconnect / preload 必须带 crossorigin，否则会因为请求模式不匹配而重复请求一次。
  • 域名收敛（把资源集中到少数几个域名）在 HTTP/2 下比域名分片（把资源打散到多个域名）更优，因为 HTTP/2 一条连接就能并发，分片反而增加握手成本。

三、TCP：面向连接的可靠传输

3.1 TCP 与 UDP 的本质区别

不要只答”TCP 可靠、UDP 不可靠”，要能说清代价：

维度 TCP UDP
连接 面向连接，需握手 无连接，直接发
可靠性 确认重传、按序交付 不保证送达、不保证顺序
拥塞控制 有，会主动降速 无，网络拥堵也照发
头部开销 20~60 字节 8 字节
传输形式 字节流（无边界） 数据报（有边界）
通信模式 一对一 支持一对多（广播/组播）
典型场景 HTTP、文件传输、邮件 DNS、视频通话、游戏、QUIC

“字节流 vs 数据报”是容易被追问的点：TCP 把数据当成连续的字节流，两次 send 的数据可能被合并成一个包（Nagle 算法）或拆成多个包，所以应用层必须自己处理粘包/拆包（用固定长度、分隔符或长度前缀）。UDP 保留消息边界，一次 send 对应一次 recv。

3.2 三次握手

sequenceDiagram
    participant C as 客户端
    participant S as 服务端

    Note over C: CLOSED
    Note over S: LISTEN
    C->>S: 1. SYN=1, seq=x
    Note over C: SYN_SENT
    Note over S: SYN_RCVD
    S->>C: 2. SYN=1, ACK=1, seq=y, ack=x+1
    Note over C: ESTABLISHED
    C->>S: 3. ACK=1, seq=x+1, ack=y+1
    Note over S: ESTABLISHED
    Note over C,S: 连接建立，可以传输数据

为什么是三次，两次不行？ 标准答案有两层，第二层才是关键：

  1. 表层解释：三次握手才能让双方都确认对方的收发能力正常。两次握手时，服务端无法确认自己的 SYN-ACK 客户端是否收到。
  2. 深层原因（RFC 793 的原话）：防止历史连接造成的资源浪费。假设客户端发出 SYN 后超时重发，旧的 SYN 在网络中滞留后又到达服务端。如果只有两次握手，服务端收到旧 SYN 就直接进入 ESTABLISHED 并分配资源；三次握手下，客户端收到针对旧 SYN 的 SYN-ACK 时会发现序列号不对，回一个 RST 终止这条连接，服务端得以及时释放资源。

为什么不是四次？ 三次已经够了，第二次握手把服务端的 SYN 和 ACK 合并发送，四次是浪费一个 RTT。

SYN 洪泛攻击：攻击者伪造大量源 IP 发 SYN 但不回第三次 ACK，服务端的半连接队列（SYN queue）被占满，正常用户无法建连。防御手段是 SYN Cookie——服务端不立即分配资源，而是把连接信息编码进初始序列号，收到 ACK 时再解码验证。

3.3 四次挥手与 TIME_WAIT

sequenceDiagram
    participant C as 客户端（主动关闭方）
    participant S as 服务端（被动关闭方）

    Note over C,S: ESTABLISHED
    C->>S: 1. FIN=1, seq=u
    Note over C: FIN_WAIT_1
    S->>C: 2. ACK=1, ack=u+1
    Note over S: CLOSE_WAIT
    Note over C: FIN_WAIT_2
    Note over S: 服务端处理剩余数据
可能持续一段时间
    S->>C: 3. FIN=1, ACK=1, seq=w
    Note over S: LAST_ACK
    Note over C: TIME_WAIT
    C->>S: 4. ACK=1, ack=w+1
    Note over S: CLOSED
    Note over C: 等待 2MSL 后 CLOSED

为什么关闭要四次而建连只要三次？ 因为 TCP 是全双工的，关闭需要两个方向各自关闭。被动方收到 FIN 时只能立刻确认”我知道你不发了”，但自己可能还有数据没发完，所以 ACK 和 FIN 不能合并（除非确实没有待发数据，此时内核可能合并，称为快速关闭）。

TIME_WAIT 为什么要等 2MSL？ MSL 是报文最大生存时间，Linux 默认 30s，所以 2MSL = 60s。两个原因：

  1. 确保最后一个 ACK 能到达对方。如果 ACK 丢失，被动方会重发 FIN，主动方在 TIME_WAIT 期间还能重发 ACK。若立即关闭，重发的 FIN 会收到 RST，被动方无法正常关闭。
  2. 让本次连接产生的所有报文在网络中消散，避免它们被后续使用相同四元组的新连接误收。

TIME_WAIT 过多的实际问题：服务端如果主动关闭大量短连接（比如反向代理回源），会积累大量 TIME_WAIT 占用端口和内存。缓解手段：开启 net.ipv4.tcp_tw_reuse（配合 timestamps）、使用长连接（HTTP Keep-Alive）从根本上减少连接数、扩大 ip_local_port_range。注意 tcp_tw_recycle 在 NAT 环境下会导致连接失败，Linux 4.12 后已移除，不要再用。

    TIME_WAIT --> CLOSED: 等待 2MSL

    CLOSE_WAIT --> LAST_ACK: 应用 close()，发 FIN
    LAST_ACK --> CLOSED: 收到 ACK

排查经验：netstat -an | grep CLOSE_WAIT 数量异常，说明应用代码没有正确关闭 socket（收到了对方的 FIN 但没调 close），这是代码 bug 而非系统配置问题；TIME_WAIT 多则通常是连接模式问题（大量短连接）。

3.5 可靠传输：序列号、确认与重传

TCP 的可靠性建立在四个机制上：

flowchart TB
    A["TCP 可靠传输"] --> B["序列号 seq

    A --> C["确认应答 ACK

    A --> D["超时重传 RTO

    A --> E["快速重传

    E --> F["SACK 选择性确认
告知对方具体缺哪一段
避免整窗重传"]

超时重传（RTO） 的时间不是固定值，而是根据采样的 RTT 动态计算（Jacobson 算法），并在连续超时时指数退避（1s → 2s → 4s…）。这解释了为什么弱网下请求会”卡很久然后突然成功”。

快速重传：接收方收到失序报文时会重复确认它期望的那个序号。发送方收到 3 个重复 ACK 就判定该段丢失，立即重传而不等 RTO。

SACK：累积确认的缺陷是只能告诉发送方”我期望第 N 个字节”，无法表达”N 丢了但 N+1 到 N+1000 我收到了”。SACK 选项在 ACK 里携带已收到的区间列表，让发送方只重传真正丢失的段。

3.6 流量控制：滑动窗口

流量控制解决的是接收方处理不过来的问题。接收方在每个 ACK 里通过窗口字段告知自己还能接收多少字节，发送方据此限制在途数据量。

窗口随着确认到来向右滑动。两个衍生考点：

  • 零窗口与窗口探测：接收方缓冲区满时通告 window=0，发送方停发并启动持续计时器，定期发窗口探测包询问是否可以恢复。若不探测，接收方后来通告的窗口更新报文一旦丢失，双方会永久死锁。
  • 糊涂窗口综合症（Silly Window Syndrome）：接收方每腾出几个字节就通告小窗口，导致大量小包传输、头部开销占比极高。解决方案在两端：接收方用 Clark 方案（等缓冲区腾出至少一个 MSS 或一半空间再通告），发送方用 Nagle 算法（攒够一个 MSS 或收到上一个 ACK 再发）。

Nagle 算法与前端的关系：Nagle 会让小数据攒批发送以提升吞吐，但增加延迟。对实时性要求高的场景（游戏、WebSocket 心跳）需要关闭它，即 TCP_NODELAY。Node.js 里对应 socket.setNoDelay(true)。

3.7 拥塞控制：四个阶段

流量控制看的是接收方能力，拥塞控制看的是网络本身的承载能力。核心变量是拥塞窗口 cwnd，实际发送量取 min(cwnd, rwnd)。

flowchart TB
    A["连接建立

关键理解：

  • 慢启动并不慢，它是指数增长，”慢”是指起点低。初始拥塞窗口（IW）从早期的 1~4 MSS 提升到现在普遍的 10 MSS（约 14KB），这也是”首屏关键资源尽量控制在 14KB 内可以在第一个 RTT 送达”这个说法的来源。
  • 超时重传比快速重传的惩罚重得多：前者 cwnd 直接归 1 重回慢启动，后者只减半。这是弱网下性能断崖式下跌的直接原因。
  • BBR 的不同思路：传统算法（Reno、CUBIC）把丢包当作拥塞信号，但在高丢包率但不拥塞的链路（如无线网络）上会误判降速。Google 的 BBR 转而测量瓶颈带宽和往返时延来估算最优发送速率，在长肥管道和弱网上提升显著。

面试追问：为什么弱网下 HTTP/2 单连接可能不如 HTTP/1.1 多连接？ 因为 HTTP/2 只有一条 TCP 连接，一旦丢包，拥塞控制降速影响所有流；HTTP/1.1 的 6 条连接各有独立的 cwnd，一条降速其他不受影响。这正是 HTTP/3 换用 QUIC 的动因之一。

四、HTTPS 与 TLS：加密的握手过程

4.1 为什么需要 HTTPS

HTTP 是明文传输，三大风险在公共网络上都真实存在：

风险 攻击场景 HTTPS 的应对
窃听 咖啡馆 WiFi 抓包看到密码 TLS 加密，抓包只能看到乱码

  • 两个随机数（Random_C 和 Random_S）参与密钥推导，增强随机性。
  • RSA 模式的缺陷：如果服务器私钥泄露，攻击者拿到历史流量可以解密出 Pre-Master 从而解密所有内容，不具备前向安全性。

4.4 TLS 1.3 握手（简化与改进）

TLS 1.3 去掉了不安全的加密套件（RSA、SHA-1、CBC 模式），强制使用具备前向安全性的密钥交换算法（ECDHE），并把握手从 2-RTT 减到 1-RTT：

sequenceDiagram
    participant C as 客户端
    participant S as 服务端

    Note over C,S: TCP 三次握手完成
    C->>S: ClientHello

    Note over C: 已发送自己的 ECDHE 公钥

优势：

  • 1-RTT 握手：客户端在第一个消息就发送密钥份额，服务器立即完成密钥协商。TLS 1.2 需要 2-RTT（第一轮协商算法，第二轮交换密钥）。
  • 前向安全性：ECDHE 每次连接生成临时密钥对，即使服务器私钥泄露，也无法解密历史会话（因为临时私钥不保存）。
  • 0-RTT 恢复（可选）：会话恢复时客户端可以在第一个包就发送加密的应用数据，彻底消除 TLS 握手延迟，但有重放攻击风险，只能用于幂等请求。

4.5 证书链与信任锚

浏览器如何验证服务器证书是真的？证书不是孤立的，而是一条信任链：

flowchart TB
    A["根证书 Root CA
预装在操作系统/浏览器
自签名"] --> B["中间证书 Intermediate CA
由根 CA 签发"]
    B --> C["服务器证书
example.com
由中间 CA 签发"]
    
    Note1["验证方向：从叶子向根
每一级验证签名 + 有效期 + 吊销状态"]
    C -.-> Note1

验证流程：

  1. 服务器在握手时发送证书链（服务器证书 + 中间证书，不含根证书）。
  2. 浏览器从服务器证书开始，用中间证书的公钥验证服务器证书的签名。
  3. 再用根证书的公钥验证中间证书的签名。
  4. 根证书是预装的信任锚，它说可信就可信。
  5. 每一级都检查有效期、域名匹配、证书用途、吊销状态（OCSP / CRL）。

常见问题：

  • 证书链不完整：服务器只发了自己的证书，没发中间证书。部分浏览器会尝试在线获取（AIA），但增加延迟；有的会直接报错。
  • 自签名证书：开发环境常见，因为没有 CA 签名，浏览器无法验证，会警告”不安全”。生产环境必须用受信任 CA 签发的证书。
  • 证书透明度（CT）：防止 CA 被入侵后偷偷签发假证书。所有公开信任的证书都要记录到公开日志，浏览器会检查 SCT（Signed Certificate Timestamp）。

面试追问：PUT 和 POST 的区别？ PUT 是幂等的且通常要求 URL 明确指定资源（PUT /users/123），客户端决定资源位置；POST 不幂等，通常用于集合 URL（POST /users），服务器决定新资源的 ID。实践中很多 API 不区分，全用 POST。

为什么有了 Last-Modified 还要 ETag？ Last-Modified 有三个缺陷：

  1. 精度只到秒。1 秒内多次修改无法识别，会误用旧缓存。
  2. 内容没变但时间变了。构建流程重新生成文件会更新 mtime，导致明明内容相同却重新下载。
  3. 分布式环境下不一致。多台服务器上同一文件的 mtime 可能不同，负载均衡切换会导致缓存失效。

ETag 是内容的指纹（通常是哈希），只要内容不变指纹就不变，精确得多。代价是服务器要计算哈希，有 CPU 开销（大文件可以用”文件大小+mtime”生成弱 ETag 折中）。

优先级：ETag 优先于 Last-Modified。两个都有时，服务器以 ETag 的比对结果为准。

7.2 HTTP/1.1 的队头阻塞

HTTP/1.1 的核心问题：一条 TCP 连接上，请求必须按顺序响应。前一个响应没回来，后面的只能排队。

浏览器的缓解手段是对同一域名开 6 条并发连接，前端的缓解手段是雪碧图、资源合并、域名分片。这些优化在 HTTP/2 下都变成了反模式。

管线化（Pipelining）为什么失败？ HTTP/1.1 规范允许一次性发多个请求而不等响应，但服务器仍必须按请求顺序返回响应。如果第一个响应很慢，后面的即使处理完了也要等——队头阻塞没有解决，只是从”客户端排队”变成”服务端排队”。加上代理实现混乱，主流浏览器默认全部禁用。

7.6 HTTP/3 与 QUIC

QUIC 建立在 UDP 之上，在用户态重新实现了可靠传输、拥塞控制和多路复用。核心改进：

改进 说明
消除 TCP 队头阻塞 每个流独立排序和重传，互不影响
更快的建连 传输层握手与 TLS 1.3 握手合并，1-RTT 建连；会话恢复可 0-RTT
连接迁移 用 Connection ID 而非四元组标识连接，WiFi 切 4G 时连接不中断
改进的丢包检测 每个包有单调递增的编号，不像 TCP 重传包复用序列号导致 RTT 采样歧义
默认加密 TLS 1.3 内置，没有明文的 QUIC

连接迁移的价值：TCP 连接由「源 IP + 源端口 + 目的 IP + 目的端口」四元组标识，手机从 WiFi 切到蜂窝网络时 IP 变了，所有 TCP 连接断开重连。QUIC 用与网络路径无关的 Connection ID，切网后连接继续，视频通话不中断。

为什么选 UDP 而不是改进 TCP？ TCP 实现在操作系统内核，升级需要用户更新系统，且中间设备（防火墙、NAT）对 TCP 有大量硬编码假设，新特性容易被丢弃。QUIC 在用户态实现，浏览器和服务端应用自己就能升级迭代。

八、同源策略与跨域

8.1 同源策略的定义

同源策略（Same-Origin Policy）是浏览器最核心的安全机制：只有协议、域名、端口完全相同的 URL 才是同源。非同源的页面无法互相读取 DOM、读取 Cookie、发起 AJAX 并读取响应。

URL A URL B 是否同源 原因
https://a.com/page https://a.com/api ✅ 完全相同
https://a.com/page http://a.com/page ❌ 协议不同
https://a.com/page https://b.com/page ❌ 域名不同
https://a.com/page https://a.com:8080/page ❌ 端口不同
https://a.com/page https://sub.a.com/page ❌ 子域名也是不同域名

注意：请求可以发出，服务器也会响应，但浏览器拦截了响应。在 Network 面板能看到响应内容，但 JS 读不到，控制台报 CORS 错误。

8.2 为什么要有同源策略

没有同源策略，恶意网站可以这样攻击：

  1. 用户登录了 bank.com，浏览器存了 Cookie。
  2. 用户访问 evil.com，evil 的 JS 发起 fetch('https://bank.com/transfer?to=attacker&amount=1000')。
  3. 请求会自动带上 bank.com 的 Cookie（用户已登录），转账成功。

同源策略阻止了 evil.com 的 JS 读取 bank.com 的响应，即使请求发出也拿不到结果。Cookie 的 SameSite 属性进一步防御（后面会讲）。

8.3 跨域资源嵌入（允许的例外）

并非所有跨域操作都被禁止。以下资源的跨域加载和执行是允许的（浏览器认为风险可控）：

标签 跨域行为 限制
<script src=""> ✅ 可加载并执行 JS 无法读取内容，但能执行（JSONP 的基础）
<link href=""> ✅ 可加载 CSS 无法读取样式表文本
<img src=""> ✅ 可显示图片 无法读取像素数据（除非配合 CORS）
<video> / <audio> ✅ 可播放 无法读取原始数据
<iframe src=""> ✅ 可嵌套 不同源的 iframe 无法访问彼此的 DOM
<form action=""> ✅ 可提交到跨域 URL 无法读取响应

这些允许的操作带来了功能（CDN 加载资源），也带来了攻击面（CSRF 正是利用了 <form> 和 <img> 可以跨域发起请求）。

8.4 CORS：可控的跨域访问

简单请求的条件（同时满足）：

  1. 方法是 GET、HEAD 或 POST
  2. 头部只包含浏览器自动加的 + 手动设置的以下头：Accept、Accept-Language、Content-Language、Content-Type（且值仅为 application/x-www-form-urlencoded、multipart/form-data、text/plain）

  • Content-Type: application/json（最常见！）
  • 方法是 PUT、DELETE

8.6 CORS 的常见坑

坑 1：Access-Control-Allow-Origin 不能是多个域名

坑 2：带凭证时不能用通配符

坑 3：预检请求不带自定义头

OPTIONS 预检请求只带浏览器自动加的头，不会带 Authorization 等自定义头。所以后端鉴权中间件要放行 OPTIONS 请求，否则会 401 导致预检失败。

8.7 JSONP：已过时的跨域方案

在 CORS 出现前，前端用 JSONP 绕过同源策略。原理：<script> 标签可以跨域，服务器返回一段 JS 代码调用预定义的回调函数。

致命缺陷：

  • 只支持 GET
  • 无法处理错误（无 HTTP 状态码）
  • 存在 XSS 风险：服务器返回的 JS 会直接执行，如果被注入了恶意代码，无法防御
  • 服务端要单独写逻辑包装成函数调用

现代项目不要再用 JSONP，一律用 CORS。

9.1 Cookie 的机制

Cookie 是浏览器存储在客户端的小段文本（每个不超过 4KB），自动随请求发送。服务器通过 Set-Cookie 响应头写入，浏览器后续请求自动带上 Cookie 请求头。

9.2 Cookie 的关键属性

属性 作用 示例
Domain 哪些域名可以读写该 Cookie Domain=.example.com 让 a.example.com 和 b.example.com 都能访问
Path 哪些路径可以读写 Path=/api 只有 /api/* 路径的请求会带这个 Cookie
Expires / Max-Age 过期时间 不设置是会话 Cookie（关浏览器即删），设置了是持久 Cookie
Secure 只在 HTTPS 下传输 防中间人窃取，生产必加
HttpOnly 禁止 JS 读取 防 XSS 窃取 Cookie，认证 Cookie 必加
SameSite 跨站请求时是否发送 防 CSRF，有 Strict / Lax / None 三个值

SameSite 的三个值（面试高频）：

值 行为 典型场景
Strict 任何跨站请求都不发送 Cookie 用户从 google.com 点链接到 bank.com，即使已登录也要重新登录（Cookie 没发）。太严格，实际很少用
Lax（默认） 跨站的顶级导航（点链接、<a> 跳转）会发 Cookie，但跨站的表单 POST、AJAX、<img> 不发 平衡安全与体验，防住了 CSRF（因为攻击通常用 POST 或 AJAX），又允许正常跳转带认证状态
None 总是发送，但必须配合 Secure（必须 HTTPS） 跨域 iframe 内的认证、第三方支付回调

9.4 Token（JWT）：无状态认证

JWT（JSON Web Token）把用户信息编码后直接发给客户端，服务器不存储。格式：Header.Payload.Signature，三段用 . 分隔。

前端每次请求带 Authorization: Bearer <token>：

服务端验证签名，解析 Payload 得知用户身份，不查数据库。

flowchart LR
    A["登录成功"] --> B["服务端生成 JWT
用密钥签名"]
    B --> C["返回给客户端"]
    C --> D["客户端存 localStorage

优点：

  • 服务端无状态，不存 Session，易扩展
  • 适合微服务和移动端

缺点：

  • 无法主动失效（除非维护黑名单，但这又变成有状态了）
  • Token 体积大（几百字节），每次请求都带，浪费带宽
  • Payload 是 base64 编码（可解码），不能存敏感信息（密码、信用卡号）

9.5 刷新令牌（Refresh Token）

JWT 的有效期通常很短（15 分钟），过期后用 Refresh Token 换新的 Access Token，Refresh Token 有效期长（7~30 天）。

  • Refresh Token 有效期长，但只用于换 Access Token，且服务端可以记录并主动撤销（存数据库或 Redis）。

9.6 Cookie vs Token 的选择

维度 Cookie + Session Token (JWT)
存储位置 浏览器 Cookie，自动发送 客户端自己存（localStorage / sessionStorage），手动发送
服务端存储 需要（Session） 不需要（无状态）
跨域 困难（需配置 CORS + SameSite=None） 容易（手动带 Authorization 头）
移动端 不方便 天然支持
失效控制 容易（删 Session） 困难（需黑名单或短有效期 + Refresh Token）
CSRF 风险 高（自动发送） 低（手动发送）
XSS 风险 低（HttpOnly 防窃取） 高（存 localStorage 可被 XSS 读取）

实践建议：

  • 传统 Web 应用（MPA、SSR）用 Cookie + Session，配合 HttpOnly 和 SameSite=Lax。
  • 前后端分离 SPA、移动端 App、微服务用 JWT，Access Token 存内存（或 sessionStorage），Refresh Token 存 localStorage，启用短有效期。

11.3 CDN 的工作原理

CDN（内容分发网络）在全球部署边缘节点，让用户从最近的节点获取资源，把物理距离带来的延迟降到最低。

flowchart TB
    U1["北京用户"] --> E1["北京边缘节点"]
    U2["上海用户"] --> E2["上海边缘节点"]
    U3["美国用户"] --> E3["美西边缘节点"]
    
    E1 -->|"未命中，回源"| O["源站
Origin Server"]
    E2 -->|"缓存命中
直接返回"| U2
    E3 -->|"未命中，回源"| O
    
    O -.->|"回源响应
并在边缘缓存"| E1
    O -.-> E3

CDN 的接入方式：把域名的 CNAME 指向 CDN 厂商提供的域名，CDN 的 DNS 会根据用户位置返回最优边缘节点 IP。

回源与缓存控制：

  • 边缘节点是否缓存、缓存多久，由源站的 Cache-Control 决定（s-maxage 专门控制共享缓存）。
  • 缓存刷新：改了文件但 CDN 还是旧的，两个手段——主动刷新（调 CDN API 清除缓存，有延迟）或改文件名（带 hash，一劳永逸）。优先用带 hash 的文件名，避免依赖刷新。

面试追问：CDN 如何处理动态内容？ 传统 CDN 只缓存静态资源。动态内容有两种做法：一是不缓存，CDN 只做加速通道（利用其优质回源链路）；二是用边缘计算（Cloudflare Workers、Vercel Edge Functions）在边缘节点运行代码，就近生成响应。

幂等性是什么 多次请求的副作用等于一次；GET/PUT/DELETE/HEAD 幂等，POST/PATCH 不幂等
PUT 和 PATCH 的区别 PUT 完整替换（幂等），PATCH 部分更新（不一定幂等）
301 和 302 的区别 永久 vs 临时；301 浏览器会缓存并更新书签，SEO 转移权重
常见状态码含义 2xx 成功、3xx 重定向、4xx 客户端错误、5xx 服务端错误；重点 200/204/301/302/304/400/401/403/404/429/500/502/503
401 和 403 的区别 401 未认证（没登录或 token 失效，该去登录）；403 已认证但无权限（登录了但角色不够）
Content-Type 常见值 application/json、application/x-www-form-urlencoded、multipart/form-data；文件上传不要手动设置（会丢 boundary）
chunked 传输编码的作用 长度未知时替代 Content-Length，支持流式响应

13.3 HTTP 缓存

问题 答题要点
强缓存和协商缓存的区别 强缓存不发请求（200 from cache）；协商缓存发请求但可能返 304 空 body
Cache-Control 的常用值 max-age、s-maxage、no-cache、no-store、private、public、immutable、must-revalidate
no-cache 和 no-store 的区别 no-cache 可存但每次要校验；no-store 完全不存
ETag 和 Last-Modified 的区别 ETag 是内容指纹更精确；Last-Modified 精度只到秒、内容不变时间可能变、分布式下不一致
ETag 优先还是 Last-Modified 优先 ETag 优先
前端缓存最佳实践 HTML 用 no-cache；带 hash 的静态资源用 max-age=31536000, immutable；接口用 no-store
为什么用 contenthash 只有文件内容变化才变，缓存利用率最高；hash 是全项目、chunkhash 是整个 chunk
不同刷新方式的缓存行为 地址栏回车：强缓存+协商都生效；F5：跳过强缓存；Ctrl+F5：都跳过

13.4 HTTPS 与安全

问题 答题要点
HTTPS 解决什么问题 窃听（加密）、篡改（完整性校验）、冒充（证书 + CA 信任链）
TLS 握手过程 ClientHello → ServerHello + 证书 → 密钥交换 → ChangeCipherSpec → Finished；TLS 1.3 只需 1-RTT
为什么用混合加密 非对称加密安全但慢，用于协商会话密钥；对称加密快，用于传输数据
什么是前向安全性 服务器私钥泄露也无法解密历史会话；ECDHE 每次生成临时密钥对，RSA 密钥交换不具备
证书链如何验证 从服务器证书向上，用上级公钥验签，直到预装的根证书；同时校验域名、有效期、吊销状态
中间人攻击如何防范 证书校验 + HSTS + 证书透明度 + 证书固定（Pinning）
HSTS 的作用 强制浏览器用 HTTPS 访问该域名，防 SSL 剥离攻击

13.5 HTTP/2 与 HTTP/3

问题 答题要点
HTTP/1.1 的队头阻塞 一条连接上响应必须按序返回；管线化没解决（改成服务端排队），浏览器已禁用
HTTP/2 的主要改进 二进制分帧、多路复用、HPACK 头部压缩、流优先级、服务端推送（已废弃）
HTTP/2 多路复用的原理 报文拆成帧，每帧带 Stream ID，多个流的帧在一条连接上交错传输，接收端按 ID 重组
HTTP/2 还有队头阻塞吗 应用层没有了，但 TCP 层有：丢包时 TCP 按序交付导致后续数据在内核等待
HTTP/3 为什么用 UDP 在用户态实现可靠传输，避免内核升级和中间设备兼容问题；每个流独立排序消除队头阻塞
QUIC 的核心特性 消除队头阻塞、1-RTT/0-RTT 建连、连接迁移（Connection ID）、内置 TLS 1.3
HTTP/2 下还要域名分片吗 不要，改为域名收敛；分片会增加额外的 DNS/TCP/TLS 开销

13.6 跨域

问题 答题要点
什么是同源策略 协议、域名、端口三者完全相同才同源；限制 DOM 访问、Cookie 读取、AJAX 响应读取
跨域请求发出去了吗 发出去了，服务器也响应了，是浏览器拦截了响应不给 JS
简单请求的条件 方法是 GET/HEAD/POST，且 Content-Type 仅为三种表单类型之一，无自定义头
什么时候触发预检 非简单请求：自定义头（如 Authorization）、Content-Type: application/json、PUT/DELETE 等方法
预检请求带 Cookie 和自定义头吗 不带；所以后端鉴权中间件必须放行 OPTIONS
带 Cookie 跨域怎么配 后端 Allow-Origin 必须是具体域名（不能 *）+ Allow-Credentials: true；前端 credentials: 'include'
JSONP 的原理和缺陷 利用 <script> 可跨域；只支持 GET、无法处理错误、有 XSS 风险，已过时
开发环境跨域怎么解决 用 devServer 代理，前端请求同源的开发服务器，由它转发（服务器之间无同源限制）

13.7 Cookie 与认证

问题 答题要点
Cookie 的关键属性 Domain、Path、Expires/Max-Age、Secure、HttpOnly、SameSite
HttpOnly 防什么 防 XSS 读取 Cookie（document.cookie 读不到）
SameSite 的三个值 Strict（全不发）、Lax（默认，顶级导航发）、None（都发但必须 Secure）
Cookie 和 Session 的关系 Cookie 存 session ID，真实数据存服务端；分布式环境需共享（Redis）
Token 和 Cookie 的区别 Token 无状态、跨域方便、移动端友好，但难主动失效、存 localStorage 有 XSS 风险
JWT 的结构 Header.Payload.Signature；Payload 是 base64 可解码，不能存敏感信息
为什么要 Refresh Token Access Token 短有效期降低泄露影响；Refresh Token 长有效期但可被服务端撤销
CSRF 如何防范 SameSite Cookie、CSRF Token（双提交或同步器模式）、校验 Origin/Referer

13.8 性能优化

问题 答题要点
输入 URL 到页面呈现的过程 URL 解析 → HSTS → 缓存检查 → DNS → TCP → TLS → HTTP 请求 → 响应 → 解析渲染
TTFB 长怎么排查 对比不同地区：差异大是网络问题（用 CDN），都慢是后端问题（查慢 SQL、加缓存）
dns-prefetch / preconnect / preload 的区别 依次做更多事：仅 DNS / DNS+TCP+TLS / 完整下载资源；开销递增
script 的 async 和 defer 区别 都并行下载；async 下载完立即执行不保证顺序，defer 等解析完按顺序执行
如何优化 LCP 降 TTFB（CDN、缓存）、preload 关键图片、用现代图片格式、消除阻塞渲染资源
gzip 和 brotli 怎么选 brotli 压缩率高 15~25%，优先用，保留 gzip 回退；图片视频不要再压缩
CDN 的工作原理 CNAME 指向 CDN，CDN 的 DNS 按用户位置返回最近边缘节点；未命中则回源并缓存
CDN 缓存刷新怎么做 优先用带 hash 的文件名（一劳永逸），其次调 CDN API 主动刷新

13.9 WebSocket

问题 答题要点
WebSocket 与 HTTP 的关系 借用 HTTP 完成握手（Upgrade: websocket + 101 状态码），之后是独立的帧协议
WebSocket 与轮询的对比 短轮询浪费请求、长轮询占连接、SSE 单向、WebSocket 全双工低延迟
WebSocket 和 SSE 怎么选 只需服务器推送用 SSE（自动重连、更轻量）；需双向或二进制用 WebSocket
WebSocket 受同源策略限制吗 不受浏览器拦截，但握手时会带 Origin 头，服务端应校验
为什么要心跳 中间设备（NAT、防火墙）会关闭空闲连接；心跳还能及时发现假死连接

十四、答题策略

知识点掌握了，表达方式同样影响结果。几个实用建议：

分层作答，先框架后细节。 被问”HTTP 缓存怎么做”时，先说”分强缓存和协商缓存两层，强缓存不发请求，协商缓存发请求但可能返 304”，再展开具体响应头。面试官能立刻判断你有没有体系，而不是零散记了几个头。

主动埋钩子，控制追问方向。 讲三次握手时提一句”这里如果考虑 SYN 洪泛攻击的话还有 SYN Cookie 机制”，面试官很可能顺着问下去——而这是你准备过的方向。

区分”规范如此”和”实践如此”。 GET 的长度限制不是 HTTP 规范规定的，是浏览器和服务器的实现限制；HTTP/2 的服务端推送在规范里存在但主流浏览器已废弃。能说清这层区别会显得对技术的理解更真实。

承认边界比硬编好。 被问到不确定的细节（比如 QUIC 的具体拥塞控制算法），说”这块我了解到的是它默认用 CUBIC 但支持插件式替换，更细的实现我没深入看过”，比编造一个错误答案好得多。面试官通常在意的是知识边界是否清晰，而非是否无所不知。

联系实际项目。 讲缓存策略时提”我们项目用 Vite 构建，产物自带 contenthash，Nginx 对带 hash 的文件配了一年强缓存，HTML 配 no-cache，上线后就不需要手动刷 CDN 了”——具体场景比背概念更有说服力。

网络这块知识的特点是层次分明、彼此关联：TCP 的拥塞控制解释了 HTTP/2 在弱网下的表现，同源策略解释了 CORS 为什么这样设计，缓存机制决定了前端工程化的产物命名规则。把这些关联串起来，回答任何一个点时都能自然延伸到相关知识，这比孤立地背诵每个概念有效得多。

OAuth 2.0 完全指南：从原理到生产实践
发表于 2026-09-20| 更新于 2026-09-15|Backend
字数总计: 13.6k|阅读时长: 69 分钟

在现代应用开发中，用户经常需要授权第三方应用访问他们在其他平台上的数据，而不想直接交出账号密码。OAuth 2.0 作为行业标准的授权框架，解决了”如何在不泄露密码的前提下，让第三方应用安全访问用户资源”这一核心问题。从微信登录、GitHub 授权，到 Google Drive API 调用，OAuth 2.0 已经成为互联网授权的事实标准。

本文从 OAuth 2.0 的使用背景出发，详细讲解四种授权模式的原理与场景、前后端完整交互流程、Express/NestJS 双框架实现、以及生产环境的安全实践。所有代码可直接用于项目。

一、为什么需要 OAuth 2.0

1.1 传统授权方式的困境

假设你开发了一个”照片打印服务”，需要访问用户存储在 Google Photos 中的照片。传统方式会遇到以下问题：

方式一：直接索要密码

存在的问题：

问题 说明
密码泄露风险 第三方应用获得完整密码，可以做任何操作
权限过大 无法限制第三方应用的访问范围（只读？全部相册？）
无法撤销 除非修改密码，否则无法单独撤销该应用的访问权限
信任问题 用户需要完全信任第三方应用
多因素认证失效 第三方应用无法通过 2FA 验证

方式二：使用特定 API Key

仍存在的问题：

  • 缺乏标准化（每个平台实现不同）
  • 权限控制粒度不够
  • 用户体验差（需要手动复制粘贴 Key）

1.2 OAuth 2.0 的解决方案

OAuth 2.0 通过授权码和**访问令牌（Access Token）**的机制，实现了”委托授权”：

sequenceDiagram
    participant U as 用户
    participant C as 照片打印服务
(客户端)
    participant A as Google
(授权服务器)
    participant R as Google Photos
(资源服务器)
    
    U->>C: 1. 点击"导入 Google Photos"
    C->>A: 2. 重定向到 Google 授权页面
    A->>U: 3. 显示授权请求
"照片打印服务想访问你的照片"
    U->>A: 4. 同意授权
    A->>C: 5. 返回授权码 (code)
    C->>A: 6. 用 code + 密钥换取 Access Token
    A->>C: 7. 返回 Access Token
    C->>R: 8. 使用 Token 请求照片列表
    R->>C: 9. 返回照片数据
    C->>U: 10. 展示照片

OAuth 2.0 的核心优势：

  • ✅ 密码安全：第三方应用永远不接触用户密码
  • ✅ 权限可控：通过 scope 精确控制授权范围（如 photos:read）
  • ✅ 可撤销：用户可以随时撤销授权，无需修改密码
  • ✅ 标准化：RFC 6749 定义，各平台统一实现
  • ✅ 时效性：Access Token 有过期时间，降低泄露风险
  • ✅ 用户体验好：统一的授权流程，无需复制粘贴

角色 说明 示例
Resource Owner 资源所有者（通常是用户） 你（拥有 Google Photos 中的照片）
Client 客户端（第三方应用） 照片打印服务的网站

注意：Authorization Server 和 Resource Server 可以是同一个服务器，也可以分离。

2.2 核心令牌类型

Token 生命周期对比：

Token 类型 有效期 用途 存储位置
Authorization Code 1-10 分钟 换取 Access Token URL 参数（临时）
Access Token 1 小时 - 1 天 访问资源 API 内存或 localStorage
Refresh Token 永久或数月 刷新 Access Token httpOnly Cookie（推荐）

三、四种授权模式详解

OAuth 2.0 定义了四种授权模式（Grant Types），适用于不同场景：

3.1 授权码模式（Authorization Code）

最安全、最常用的模式，适用于有后端的 Web 应用。

sequenceDiagram
    participant U as 用户浏览器
    participant C as 客户端后端
    participant A as 授权服务器
    participant R as 资源服务器
    
    Note over U,R: 第一阶段：获取授权码
    U->>C: 1. 点击"使用 GitHub 登录"
    C->>U: 2. 重定向到授权页面
GET /authorize?response_type=code&client_id=xxx&redirect_uri=xxx&scope=xxx
    U->>A: 3. 跳转到 GitHub 授权页面
    A->>U: 4. 显示授权确认页面
    U->>A: 5. 用户点击"同意授权"
    A->>U: 6. 重定向回应用
GET /callback?code=AUTH_CODE&state=xxx
    
    Note over U,R: 第二阶段：换取 Access Token
    U->>C: 7. 浏览器携带 code 访问回调地址
    C->>A: 8. 用 code 换取 token
POST /token
{code, client_id, client_secret}
    A->>C: 9. 返回 Access Token + Refresh Token
    
    Note over U,R: 第三阶段：访问资源
    C->>R: 10. 使用 Access Token 请求用户信息
Authorization: Bearer ACCESS_TOKEN
    R->>C: 11. 返回用户数据
    C->>U: 12. 返回登录成功

关键特点：

  • ✅ Access Token 不经过浏览器，最安全
  • ✅ 使用 client_secret 验证客户端身份
  • ✅ 支持 Refresh Token 长期访问

适用场景：

  • 传统 Web 应用（有后端服务器）
  • 移动应用（需要配置 custom URL scheme）

3.2 隐式授权模式（Implicit）

已不推荐使用，授权服务器直接在重定向 URL 中返回 Access Token。

sequenceDiagram
    participant U as 用户浏览器
    participant A as 授权服务器
    participant R as 资源服务器
    
    U->>A: 1. 重定向到授权页面
response_type=token
    A->>U: 2. 用户同意授权
    A->>U: 3. 重定向回应用
/callback#access_token=xxx
    U->>R: 4. 使用 Access Token 访问资源
    R->>U: 5. 返回数据

为什么不推荐？

  • ❌ Access Token 暴露在 URL 中，浏览器历史记录可能泄露
  • ❌ 无法验证客户端身份（没有 client_secret）
  • ❌ 不支持 Refresh Token

现代替代方案： 使用 PKCE 增强的授权码模式（见 3.5 节）

3.3 密码模式（Resource Owner Password Credentials）

用户直接在客户端输入账号密码，由客户端转发给授权服务器。

sequenceDiagram
    participant U as 用户
    participant C as 客户端
    participant A as 授权服务器
    
    U->>C: 1. 输入用户名 + 密码
    C->>A: 2. POST /token
{username, password, client_id, client_secret}
    A->>A: 3. 验证凭据
    A->>C: 4. 返回 Access Token
    C->>U: 5. 登录成功

适用场景：

  • 第一方应用（自家的移动 App）
  • 从传统用户名密码认证迁移到 OAuth 2.0

安全风险：

  • ⚠️ 客户端接触用户密码，违背 OAuth 初衷
  • ⚠️ 仅适用于高度信任的客户端

示例请求：

3.4 客户端凭证模式（Client Credentials）

**机器对机器（M2M）**通信，不涉及用户，客户端以自己的名义访问资源。

sequenceDiagram
    participant C as 客户端服务器
    participant A as 授权服务器
    participant R as 资源服务器
    
    C->>A: 1. POST /token
{client_id, client_secret, grant_type=client_credentials}
    A->>A: 2. 验证客户端身份
    A->>C: 3. 返回 Access Token
    C->>R: 4. 使用 Token 访问资源
    R->>C: 5. 返回数据

适用场景：

  • 微服务间调用
  • 后台任务（如定时同步数据）
  • CLI 工具访问 API

3.5 PKCE 增强的授权码模式（推荐）

Proof Key for Code Exchange（PKCE），专为公共客户端（无法安全存储 client_secret）设计，如单页应用（SPA）、移动 App。

sequenceDiagram
    participant U as 用户浏览器
    participant C as 单页应用(SPA)
    participant A as 授权服务器
    
    Note over U,A: 准备阶段
    C->>C: 1. 生成随机 code_verifier
例: dBjftJeZ4CVP-mB92K27uhbUJU1p1r_wW1gFWFOEjXk
    C->>C: 2. 计算 code_challenge
SHA256(code_verifier) -> Base64Url
    
    Note over U,A: 授权阶段
    C->>A: 3. 重定向到授权页面
+ code_challenge + code_challenge_method=S256
    A->>U: 4. 用户同意授权
    A->>C: 5. 返回授权码 code
    
    Note over U,A: 换取 Token
    C->>A: 6. POST /token
{code, code_verifier}
    A->>A: 7. 验证: SHA256(code_verifier) == code_challenge
    A->>C: 8. 返回 Access Token

核心原理：

  1. 客户端生成随机字符串 code_verifier
  2. 计算其哈希值 code_challenge = SHA256(code_verifier)
  3. 授权请求时发送 code_challenge
  4. 换取 Token 时发送原始 code_verifier
  5. 授权服务器验证哈希是否匹配

为什么安全？

  • ✅ 即使授权码 code 被截获，攻击者没有 code_verifier 也无法换取 Token
  • ✅ 不需要 client_secret，适合无法安全存储密钥的客户端

9.1 核心问题：如何关联用户与 OAuth Token？

在 OAuth 2.0 流程中，关键问题是如何将第三方平台的 Access Token 与应用的用户关联起来。

    U->>App: 1. 点击"导入 Google Photos"

9.6 总结

OAuth Token 关联的核心流程：

  1. 授权时：用户同意授权 → 换取 Token → 存储到数据库（关联 userId + provider）
  2. 使用时：从数据库查询 Token → 检查是否过期 → 调用第三方 API
  3. 优化：使用 Redis 缓存 Token，减少数据库查询
  4. 安全：Token 加密存储，定期清理过期数据

这样就实现了”用户与 OAuth Token 的持久化关联”，后续无需重复授权即可访问用户的第三方资源。

十、总结

10.1 OAuth 2.0 核心要点

  • ✅ 授权而非认证：OAuth 2.0 设计用于授权（访问资源），不是认证（验证身份），虽然常用于登录
  • ✅ 四种授权模式：授权码模式（最安全）、PKCE（SPA/移动）、客户端凭证（M2M）、密码模式（谨慎使用）
  • ✅ 三个关键令牌：Authorization Code（一次性）、Access Token（短期）、Refresh Token（长期）
  • ✅ 安全第一：使用 state 防 CSRF、验证 redirect_uri、使用 HTTPS、密钥轮换
  • ✅ 用户体验：统一授权流程、清晰的权限说明、支持账号合并

10.2 技术选型建议

场景 推荐方案
传统 Web 应用（有后端） 授权码模式
单页应用（SPA） PKCE 增强授权码模式
移动应用 PKCE + Custom URL Scheme
微服务间调用 客户端凭证模式
第三方应用授权 授权码模式 + Scope 控制
企业内部 SSO OAuth 2.0 + OpenID Connect

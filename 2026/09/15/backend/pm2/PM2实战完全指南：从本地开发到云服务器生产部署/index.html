PM2 实战完全指南：从本地开发到云服务器生产部署
发表于 2026-09-15| 更新于 2026-09-15|Backend
字数总计: 9.7k|阅读时长: 40 分钟

Node.js 服务上线最容易被低估的一件事，是「怎么让它一直活着」。本地 node app.js 跑得好好的，扔到服务器上用 nohup 一挂，SSH 断开进程还在但没人知道它什么时候挂了；改一行代码要手动 kill 再重启，重启那两秒的请求全变成 502；机器 16 核，服务只用了 1 核；某天磁盘满了，才发现日志文件已经涨到 40 GB。

PM2 解决的就是这一类问题。它是 Node.js 生态里的进程管理器：负责守护进程、崩溃自动重启、多核负载均衡、零停机重载、日志收集与切割、开机自启。本文按七段推进：使用背景与选型、本地安装与快速上手、常用命令详解、ecosystem 配置文件、Express 与 NestJS 的实战集成、云服务器部署与零停机发布、日志监控与常见问题处理。所有代码基于 PM2 5.4+ 和 Node.js 20+。

一、为什么需要 PM2

1.1 三个典型场景

场景 没有 PM2 有了 PM2
进程意外退出 未捕获异常导致进程死掉，服务全挂，等用户投诉才发现 自动重启并记录退出原因，秒级恢复
发布新版本 kill 掉旧进程再启动新进程，中间几秒请求全部失败 pm2 reload 逐个替换 worker，请求不中断
多核利用率 单进程只吃满 1 个核，剩下 15 个核闲着 cluster 模式启动 N 个 worker，内核负载均衡

1.2 PM2 在部署链路中的位置

PM2 不是 Web 服务器，也不替代 Nginx。它站在操作系统与应用进程之间，管的是「进程活着、有几个、日志去哪」：

flowchart LR
  Client["客户端"] --> Nginx["Nginx
TLS · 静态资源 · 反向代理"]
  Nginx --> PM2["PM2 God Daemon
负载均衡 · 守护 · 日志"]
  PM2 --> W1["Worker 0
Node 进程"]
  PM2 --> W2["Worker 1
Node 进程"]
  PM2 --> W3["Worker N
Node 进程"]
  W1 --> DB[("MySQL / Redis")]
  W2 --> DB
  W3 --> DB
  Systemd["systemd"] -.->|"开机拉起 PM2"| PM2

1.3 和其他方案怎么选

方案 适合场景 短板
nohup / screen 临时跑个脚本 不守护、不重启、无日志管理，机器重启就没了
PM2 单机或少量机器跑 Node 服务，需要 cluster、reload、日志 自身是单机工具，跨机编排要靠别的东西
systemd 系统级守护，非 Node 服务同样适用 没有 cluster 负载均衡和零停机 reload，配置更啰嗦
Docker + K8s 多服务、多机、需要弹性伸缩 心智负担和基础设施成本高

实践中的组合是这样的：单机部署用 systemd 拉起 PM2，PM2 管 Node 进程；上了容器就换成「一个容器一个前台 Node 进程 + K8s 负责重启和扩缩」，此时 PM2 通常不再需要（详见 8.7）。

1.4 核心概念

概念 含义
God Daemon PM2 的常驻守护进程，所有应用都是它的子进程，它挂了才会真的全挂
App / Process 被管理的一个应用，有唯一的 name 和 id
fork 模式 单进程启动，PM2 只做守护和重启，适合有状态服务、定时任务
cluster 模式 基于 Node cluster 起多个 worker 共享端口，适合无状态 HTTP 服务
ecosystem 文件 ecosystem.config.js，把启动参数、环境变量、实例数固化成代码
reload 逐个重启 worker 实现零停机；restart 是全部杀掉再起，会中断

fork 与 cluster 的区别是新手最容易混淆的点：

flowchart TB
  subgraph Fork["fork 模式"]
    F0["PM2"] --> F1["单个 Node 进程
自己监听 3000"]
  end
  subgraph Cluster["cluster 模式"]
    C0["PM2 Master
监听 3000"] --> C1["Worker 0"]
    C0 --> C2["Worker 1"]
    C0 --> C3["Worker 2"]
    C0 --> C4["Worker 3"]
  end

cluster 模式下多个进程能监听同一个端口，是因为主进程持有 listen socket 并把连接分发给 worker，不需要你改一行业务代码。代价是进程内状态不再共享：内存里的 Session、本地缓存、setInterval 定时任务都会变成 N 份，这也是 5.4 和 8.4 要专门处理的问题。

2.3 本地开发要不要用 PM2

本地开发的热重载用 nodemon 或框架自带的 watch 更顺手（nest start --watch、tsx watch）。PM2 在本地的价值主要是两个：

  1. 同时跑多个服务：一条 pm2 start ecosystem.config.js 把 API、Worker、定时任务全拉起来，pm2 logs 聚合看日志，比开五个终端窗口省事。
  2. 验证 cluster 行为：多进程下的 Session、缓存、定时任务问题必须在本地用 cluster 模式复现，否则一定会在生产上撞到。

三、常用命令详解

3.1 生命周期管理

restart 和 reload 的差别在生产环境里非常关键：

sequenceDiagram
  participant U as 客户端
  participant P as PM2
  participant W0 as Worker 0
  participant W1 as Worker 1

  Note over P: pm2 restart（有中断）
  P->>W0: SIGINT 杀掉
  P->>W1: SIGINT 杀掉
  U->>P: 请求
  P--xU: 502 无可用进程
  P->>W0: 启动新进程
  P->>W1: 启动新进程

  Note over P: pm2 reload（零停机）
  P->>W0: 启动新 Worker 0'
  W0'-->>P: ready
  P->>W0: SIGINT 优雅退出
  U->>P: 请求
  P->>W1: 转发（旧进程仍在服务）
  W1-->>U: 200
  P->>W1: 再替换 Worker 1

规则很简单：cluster 模式下发布用 reload，fork 模式只能 restart（单进程没有备胎可以轮换）。

3.2 查看状态与日志

排查问题时最有用的是 pm2 describe，它会直接给出 exit code 和 restart time——进程反复重启时，退出码往往一眼就能定位原因（1 是未捕获异常，137 是被 OOM killer 干掉）。

3.3 扩缩容

只有 cluster 模式支持 scale。实例数的经验值是 CPU 核数（-i max）或 核数 - 1（-i -1，留一个核给系统和 Nginx）。起得比核数多不会更快，反而增加上下文切换和内存开销——每个 Node 进程的基础内存占用在 50–80 MB。

3.4 保存与自启

这是最容易被漏掉的一步。PM2 的进程列表默认只存在内存里，机器重启就没了：

pm2 startup 本质是生成一个 systemd unit 来拉起 PM2 daemon，daemon 起来后从 dump.pm2 恢复应用。所以顺序不能错：每次改完进程列表都要重新 pm2 save，否则重启后恢复的还是老配置。

参数 建议值 理由
instances HTTP 服务 max 或 -1；Worker 1 超过核数无收益，还多吃内存

8.7 常见问题：Docker 里还要不要用 PM2

结论是通常不要。容器编排（Docker restart policy、K8s）已经承担了守护与重启，PM2 再套一层会带来两个实际问题：

  1. 信号被吞：PM2 作为 PID 1 时，docker stop 发的 SIGTERM 可能没有正确传递到业务进程，导致优雅退出失效
  2. 健康状态失真：业务进程崩了但 PM2 还活着，容器状态仍是 healthy，编排系统不会重建它

九、上生产前的检查清单

  • 用 ecosystem.config.js 启动，配置进仓库，不靠命令行参数
  • HTTP 服务用 cluster 模式，instances 为 max 或 -1
  • Worker、定时任务用 fork 模式且只起 1 个实例
  • 代码里发了 process.send('ready')，配置里开了 wait_ready
  • 监听 SIGINT 和 SIGTERM，server.close() 后再退出，有超时兜底
  • kill_timeout 大于最慢接口耗时
  • max_memory_restart、min_uptime、max_restarts 都已设置
  • 已装 pm2-logrotate，配好 max_size 与 retain
  • 日志写 stdout/stderr，结构化并带 worker 标识，不含敏感信息
  • Session、缓存、限流计数已外置到 Redis，进程内无共享状态
  • 定时任务不会因多实例重复执行
  • 有 /healthz 健康检查，发布脚本会探活并能自动回滚
  • 执行过 pm2 save + pm2 startup，并真的重启机器验证过
  • 用非 root 用户运行，应用端口只监听 127.0.0.1
  • 已在本地用 cluster 模式跑通过一遍，而不是只测了 fork
  • 容器化部署时用 pm2-runtime 或干脆去掉 PM2

十、小结

PM2 的命令不多，真正的难点在于理解它管什么、不管什么。它管进程活着、有几个、日志去哪；它不管你的应用是否正确响应信号、状态是否可以被多进程共享、请求是否被优雅地处理完。零停机发布之所以经常「配了但没用」，就是因为前半句是 PM2 的事，后半句是应用代码的事。

按重要性排序，最值得先做对的三件事：

  1. 优雅启停闭环——ready 信号 + server.close() + 合理的 kill_timeout，这是 reload 不掉请求的全部前提
  2. 状态外置——从 fork 到 cluster 的迁移成本几乎全在这里，Session、缓存、定时任务三处必查
  3. 日志切割与自启——pm2-logrotate 和 pm2 save && pm2 startup 各一行命令，却是最常见的两类生产事故来源

至于要不要长期用 PM2：单机或几台机器的 Node 服务，PM2 是投入产出比最高的选择，一个配置文件就能拿到 cluster、零停机和日志管理。等到服务数量上来、需要跨机调度和弹性伸缩，再迁到容器与 K8s，届时把 PM2 换成「一容器一前台进程」——本文里关于优雅启停和状态外置的功课，在那个阶段一行都不会浪费。

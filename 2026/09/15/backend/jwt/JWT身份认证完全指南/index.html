JWT 身份认证完全指南：从原理到生产实践
发表于 2026-09-15| 更新于 2026-09-14|Backend
字数总计: 8.3k|阅读时长: 40 分钟

在前后端分离的时代，Session + Cookie 的认证方案逐渐暴露出跨域、分布式扩展、移动端适配等问题。JWT（JSON Web Token）作为无状态认证方案，用一个自包含的 token 完成身份传递，让服务端不再需要存储会话状态。但它的”无状态”特性也带来了新的挑战：token 无法主动失效、续期策略需要精心设计、安全边界更依赖密钥管理。

本文从 JWT 的使用背景出发，覆盖前后端交互流程、token 生成与验证、过期无感刷新、Express/NestJS 双框架实现、与其他方案的对比，以及生产环境的安全实践。所有代码可直接用于项目。

一、为什么需要 JWT

1.1 传统 Session 的困境

在传统的 Web 应用中，服务端使用 Session + Cookie 维护用户状态：

sequenceDiagram
    participant Client
    participant Server
    participant SessionStore
    
    Client->>Server: 1. 登录请求 (username/password)
    Server->>SessionStore: 2. 创建 Session
    SessionStore-->>Server: 3. Session ID
    Server-->>Client: 4. Set-Cookie: sessionId=xxx
    
    Client->>Server: 5. 业务请求 (带 Cookie)
    Server->>SessionStore: 6. 查询 Session
    SessionStore-->>Server: 7. 返回用户信息
    Server-->>Client: 8. 返回业务数据

Session 方案的痛点：

问题 说明
跨域问题 Cookie 默认不跨域，前后端分离时需要配置 CORS + withCredentials
分布式扩展 Session 存储在单机内存中，多机部署需要 Session 共享（Redis）或粘性会话
移动端不友好 App、小程序没有 Cookie 机制，需要手动管理 Session ID
CSRF 风险 Cookie 自动携带，容易遭受跨站请求伪造攻击
存储压力 大量在线用户时，Session 存储会成为性能瓶颈

1.2 JWT 的解决方案

JWT 通过自包含的 token 将用户信息编码到 token 本身，服务端无需存储：

sequenceDiagram
    participant Client
    participant Server
    
    Client->>Server: 1. 登录请求 (username/password)
    Server->>Server: 2. 验证用户 + 生成 JWT
    Server-->>Client: 3. 返回 JWT token
    
    Client->>Server: 4. 业务请求 (Authorization: Bearer token)
    Server->>Server: 5. 验证 JWT 签名 + 解码
    Server-->>Client: 6. 返回业务数据

JWT 的优势：

  • ✅ 无状态：服务端不存储 token，天然支持水平扩展
  • ✅ 跨域友好：通过 HTTP Header 传递，不受同源策略限制
  • ✅ 移动端友好：与平台无关，任何客户端都能使用
  • ✅ 自包含：token 携带用户信息，减少数据库查询
  • ✅ 标准化：RFC 7519 规范，各语言都有成熟库

二、JWT 结构与原理

2.1 JWT 的三段式结构

一个完整的 JWT 由三部分组成，用 . 分隔：

Header（头部）

声明 token 类型和签名算法：

Payload（负载）

存放实际数据，包括标准字段和自定义字段：

⚠️ 注意：Payload 是 Base64Url 编码（非加密），任何人都能解码查看，不要存放敏感信息（如密码、银行卡号）。

Signature（签名）

防止 token 被篡改：

客户端无法伪造签名（不知道 secret），服务端验证签名即可确认 token 未被篡改。

3.2 双 Token 策略

生产环境推荐使用 Access Token + Refresh Token 双 token 机制：

Token 类型 用途 有效期 存储位置
Access Token 访问业务接口 15分钟 - 1小时 内存或 localStorage
Refresh Token 刷新 Access Token 7天 - 30天 httpOnly Cookie（推荐）或 localStorage

为什么需要两个 token？

  • Access Token 短期有效，即使泄露影响范围小
  • Refresh Token 长期有效但只用于刷新，减少暴露频率
  • Refresh Token 可以存储在服务端（可撤销），弥补 JWT 无法主动失效的问题

5.1 Token 存储方案对比

方案 安全性 优点 缺点 适用场景
localStorage ⭐⭐ 简单易用，页面刷新不丢失 易受 XSS 攻击 内部系统、低安全要求
sessionStorage ⭐⭐ 关闭标签页自动清除 新标签页需要重新登录 临时会话

  • Refresh Token：存储在 httpOnly Cookie（服务端设置），前端无法通过 JS 读取

6.2 各方案详细分析

Session + Cookie

工作原理：

sequenceDiagram
    Client->>Server: 登录
    Server->>SessionStore: 创建 Session
    Server-->>Client: Set-Cookie: sessionId=abc123
    Client->>Server: 请求（自动携带 Cookie）
    Server->>SessionStore: 查询 Session
    Server-->>Client: 返回数据

优点：

  • 服务端完全控制会话，可立即撤销
  • 传统框架原生支持，实现简单
  • 适合单体应用

缺点：

  • 分布式部署需要 Session 共享（Redis/Memcached）
  • 跨域需要复杂配置（withCredentials + CORS）
  • 移动端需要手动管理 Session ID
  • CSRF 攻击风险

适用场景：

  • 传统 Web 应用（服务端渲染）
  • 内部管理系统
  • 用户规模可控的单体应用

JWT（JSON Web Token）

工作原理：

sequenceDiagram
    Client->>Server: 登录
    Server->>Server: 生成 JWT
    Server-->>Client: 返回 token
    Client->>Server: 请求（Header: Bearer token）
    Server->>Server: 验证签名 + 解码
    Server-->>Client: 返回数据

优点：

  • 无状态，天然支持分布式
  • 自包含用户信息，减少数据库查询
  • 跨域友好，移动端友好
  • 标准化（RFC 7519）

缺点：

  • 无法主动失效（需要黑名单或短期 token）
  • Payload 过大会增加网络传输
  • 密钥泄露影响面大
  • 续期策略复杂（需要 Refresh Token）

适用场景：

  • 前后端分离应用
  • 微服务架构（服务间认证）
  • RESTful API
  • 移动应用/小程序

OAuth 2.0

工作原理（授权码模式）：

sequenceDiagram
    participant User
    participant Client
    participant AuthServer
    participant ResourceServer
    
    User->>Client: 1. 点击"使用 GitHub 登录"
    Client->>AuthServer: 2. 重定向到授权页面
    User->>AuthServer: 3. 同意授权
    AuthServer-->>Client: 4. 返回授权码 (code)
    Client->>AuthServer: 5. 用 code 换取 Access Token
    AuthServer-->>Client: 6. 返回 Access Token
    Client->>ResourceServer: 7. 使用 token 访问用户资源
    ResourceServer-->>Client: 8. 返回用户数据

优点：

  • 适合第三方授权（微信、GitHub 登录）
  • 权限范围可精细控制（scope）
  • 支持多种授权模式

缺点：

  • 实现复杂度高
  • 需要额外的授权服务器
  • 不适合简单场景

适用场景：

  • 第三方授权登录
  • 开放平台（提供给第三方调用）
  • 多应用统一登录（SSO）

API Key

工作原理：

优点：

  • 实现极简
  • 适合服务间调用
  • 长期有效

缺点：

  • 无用户信息
  • 权限控制粗糙
  • 密钥泄露风险高

适用场景：

  • OpenAPI（Stripe、OpenAI）
  • 服务间调用
  • 测试环境快速验证

七、生产环境安全实践

7.1 密钥管理

建议：

  • ✅ 使用 256 位以上的随机密钥
  • ✅ Access Token 和 Refresh Token 使用不同密钥
  • ✅ 定期轮换密钥（支持多个密钥并存验证）
  • ✅ 生产环境使用密钥管理服务（AWS Secrets Manager、HashiCorp Vault）

7.2 Token 有效期设置

原则：

  • Access Token 越短越安全，但刷新频率越高
  • Refresh Token 存储在 httpOnly Cookie 可以设置更长
  • 敏感操作（修改密码、支付）需要二次验证

九、总结

9.1 JWT 最佳实践清单

  • ✅ 使用双 Token 策略：Access Token (15分钟) + Refresh Token (7天)
  • ✅ 密钥管理：使用环境变量或密钥管理服务，定期轮换
  • ✅ 存储安全：Access Token 存内存，Refresh Token 用 httpOnly Cookie
  • ✅ 实现黑名单：使用 Redis 实现 token 撤销机制
  • ✅ 速率限制：防止暴力破解和 token 重放攻击
  • ✅ HTTPS Only：生产环境强制使用 HTTPS
  • ✅ 审计日志：记录登录、登出、刷新等关键操作
  • ✅ 错误处理：区分 token 过期、无效、撤销等不同场景
  • ✅ 前端无感刷新：使用拦截器自动刷新 token，提升用户体验
  • ✅ 跨域配置：正确配置 CORS，避免 cookie 被拦截

9.2 何时不应该用 JWT

  • ❌ 需要立即撤销 token（除非实现黑名单）
  • ❌ 用户会话状态复杂（如购物车、草稿箱）
  • ❌ 传统单体应用，无需跨域和移动端
  • ❌ Payload 数据量大（JWT 每次请求都传输）

9.3 技术栈推荐

场景 推荐方案
前后端分离 + RESTful API JWT (Access + Refresh Token)
微服务架构 JWT + API Gateway
传统 Web 应用 Session + Cookie
移动应用/小程序 JWT
第三方授权登录 OAuth 2.0
OpenAPI/服务间调用 API Key 或 JWT
企业级 SSO OAuth 2.0 + JWT 或 SAML

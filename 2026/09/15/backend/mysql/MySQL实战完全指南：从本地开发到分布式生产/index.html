关系型数据库是后端服务的地基，而地基出问题的时候，症状往往长得不像数据库问题：接口偶发超时、订单金额算错、部署新版本后连接数打满、主从切换完发现少了几条数据。这些问题的根源通常是同一批基础知识没打牢——索引怎么被用到、事务隔离级别意味着什么、复制是异步的这件事对业务意味着什么。

本文假设你完全没用过 MySQL，从「为什么要这样做」讲起：使用背景与选型、本地安装与快速上手、核心语法与概念（JOIN、聚合、索引、事务这些都从零解释，配图说明）、Express 与 NestJS 的实战集成、云服务器部署与生产配置、分布式场景下的状态同步与常见问题处理。所有代码基于 MySQL 8.0+ 和 Node.js 20+。

不需要按顺序读完。如果只想先跑起来，看第二章；如果是来解决具体问题的，直接跳第八章。完全没接触过服务端部署的话，1.4 节先把「实例」「Pod」这几个词对齐，后面的配置公式才好懂。

一、为什么选 MySQL

1.1 什么场景该用它

场景 用 MySQL 不该用 MySQL
有事务的业务数据 订单、账务、库存扣减，需要 ACID 保证一致性 —
结构化关联查询 用户-订单-商品多表 JOIN、聚合报表 图关系深度遍历（用 Neo4j）
热点缓存 — 高频读取的临时数据（用 Redis）

1.4 先对齐几个名词：实例、Pod、容器

后面章节会反复出现「实例」这个词，但它在不同语境下指的是两个完全不同的东西，这是新手最容易糊的地方。先花两分钟把词对齐，后面看配置公式就不会懵。

什么是「MySQL 实例」

一个 MySQL 实例 = 一个正在运行的 mysqld 进程 + 它管理的那批数据文件。

注意区分三个层次，很多人会混：

概念 是什么 类比
实例（Instance） 一个 mysqld 进程，占一个端口（默认 3306） 一整个图书馆
库（Database / Schema） 实例里的一个命名空间，CREATE DATABASE shop 图书馆里的一个楼层
表（Table） 库里的一张二维表 楼层里的一个书架

一个实例可以装很多个库。所以「我要给新项目单独建个数据库」通常只需要 CREATE DATABASE，不需要新开一个实例。

什么是「应用实例」

同一个词的另一个含义：你的 Node.js 程序跑起来的一个进程。

线上为了抗住流量和避免单点故障，同一份代码通常会同时跑好几份：

3 个应用实例、每个池子 10 条连接 = 数据库要承受 30 条连接。这就是 4.3 节那个公式的来源。

判断当下在说哪个「实例」：谈连接池、部署、扩容，说的是应用实例；谈端口、max_connections、主从，说的是 MySQL 实例。

什么是「Pod」

Pod 是 Kubernetes（K8s）里的概念。如果你还没用 K8s，可以先简单理解成「一个应用实例的运行单位」。

三个概念的包含关系：

概念 一句话
镜像 Image 打包好的「代码 + 运行环境」，是静态文件，像一个 .zip
容器 Container 镜像跑起来的进程，有自己隔离的文件系统和网络
Pod K8s 的调度单位，通常里面就一个容器（也可以多个共享网络）
副本数 replicas 同一个 Pod 复制几份，replicas: 8 就是 8 个应用实例

所以文中说「跑 8 个 Pod」，意思就是「有 8 个应用实例在同时服务」——每个都有自己的连接池。这也解释了一类线上事故：开发在本地测试时只有 1 个进程、池子设 50 条连接毫无问题，上线后 K8s 扩到 20 个 Pod，连接数瞬间变成 20 × 50 = 1000 条，数据库直接报 Too many connections。

没用 K8s 的话，「Pod」可以直接换成「PM2 的进程数」「Docker 容器数」「部署的服务器台数」——本质都是「同时跑着几份你的代码」。

这里有个容易忽略的点：Node.js 用 PM2 的 cluster 模式或 cluster 模块时，每个 worker 进程都有独立的连接池。-i 4 意味着连接数要乘以 4，不是所有 worker 共享一个池子。

3.3 JOIN：把分散在多张表的数据拼起来

为什么数据要拆成多张表？ 假设你要存订单，最直觉的做法是一张大表全放进去：

id order_no 用户名 用户手机 用户地址 金额
1 NO001 张三 138xxxx 北京朝阳 199
2 NO002 张三 138xxxx 北京朝阳 88
3 NO003 李四 139xxxx 上海浦东 500

问题很快出现：张三下了 100 单，他的手机号就存了 100 遍。他要改手机号，你得更新 100 行——一旦漏掉几行，数据就自相矛盾了（这叫数据冗余和更新异常）。

正确做法是拆成两张表，用一个 ID 关联：

改手机号只需改 users 一行。但代价是：查询时要把两张表拼回去——这就是 JOIN 存在的理由。

场景：订单列表页要显示下单人姓名。订单表里只有 user_id，姓名在 users 表：

LEFT JOIN：左边全要，右边没有就填 NULL

场景变一下：运营要看「所有用户的下单情况」，包括那些一单都没下的用户（好去做召回）。

用 INNER JOIN 会漏掉零订单用户——因为他们在 orders 表里根本没有对应行。LEFT JOIN 就是为这个场景设计的：

假设新增了一个用户王五，从没下单：

name order_no amount
张三 NO001 199
张三 NO002 88
李四 NO003 500
王五 NULL NULL

王五保留了下来，只是右表的列是 NULL。

最容易踩的坑：LEFT JOIN 的过滤条件写在 ON 还是 WHERE，结果完全不同。

记法：ON 决定「怎么配对」，WHERE 决定「配完之后留哪些」。左表要保底，条件就得写在 ON 里。

3.4 聚合：把很多行压成一行统计值

使用背景：所有「统计类」需求都靠它。日活多少、今天营收多少、每个用户下了几单、客单价是多少——这些都不是「查数据」，而是「算数据」。

不用聚合的话，你得把 10 万行订单全查到 Node.js 里再用 reduce 累加。这既浪费带宽（传 10 万行只为得到一个数字），又慢得多（MySQL 算聚合是 C 写的，且能利用索引）。能在数据库算的统计就别搬到应用层算。

常用的五个聚合函数：

函数 作用 典型用途
COUNT(*) 行数 订单量、注册数
COUNT(DISTINCT x) 去重后的个数 日活用户数（同一用户下 3 单只算 1 个人）
SUM(x) 求和 当日营收
AVG(x) 平均 客单价
MAX(x) / MIN(x) 最大/最小 最高单笔金额

COUNT(*) 和 COUNT(列名) 有个坑：COUNT(列名) 会跳过 NULL。上面 LEFT JOIN 的例子里用 COUNT(o.id) 而不是 COUNT(*)，正是因为王五那行的 o.id 是 NULL，COUNT(o.id) 才能正确地算出 0；用 COUNT(*) 会数成 1。

WHERE 和 HAVING 的区别

这是聚合里第二个高频困惑点。两者都是「过滤」，但发生在不同阶段：

flowchart LR
  A["① 全部原始行"] -->|"WHERE
过滤单行"| B["② 符合条件的行"]
  B -->|"GROUP BY
分堆"| C["③ 分组"]
  C -->|"聚合函数
算出统计值"| D["④ 每组一行结果"]
  D -->|"HAVING
过滤统计结果"| E["⑤ 最终结果"]
  E -->|"ORDER BY / LIMIT"| F["⑥ 排序分页"]

判断标准很简单：过滤条件里用到了聚合函数（SUM/COUNT/AVG…），就必须用 HAVING；否则用 WHERE。

为什么不能写 WHERE SUM(amount) > 1000？因为 WHERE 执行时还没分堆，SUM 根本还不存在。而且性能上应尽量把条件放在 WHERE——先过滤掉不需要的行，参与分组的数据就少了。

3.7 索引：为什么加了它快 1000 倍

如果只能学一个 MySQL 优化知识点，就是索引。绝大多数「数据库好慢」的问题，答案都是索引。

没有索引时 MySQL 在做什么

想象一本 500 页的书没有目录，你要找「第 8 章」，只能从第 1 页开始一页页翻。数据库也一样——没有索引的查询叫全表扫描：把 100 万行全部读出来，逐行检查是否满足条件。

  • 无索引：读 100 万行，逐行比较 user_id，找到 5 行。慢，且随数据增长线性变慢
  • 有索引：直接定位到那 5 行。快，且数据涨到 1 亿行也只慢一点点

索引的本质是一棵排好序的树（B+ 树）。因为有序，查找时每次能排除一半以上的数据：

flowchart TB
  Root["根节点
1000 · 5000"] --> N1["100 · 500"]
  Root --> N2["2000 · 3000"]
  Root --> N3["6000 · 8000"]
  N2 --> L1["叶子：1001 → 行地址
1002 → 行地址"]
  N2 --> L2["叶子：2100 ...
2200 ..."]
  Find["查 user_id = 1001"] -.->|"① 1001 在 1000~5000 之间"| Root
  Root -.->|"② 走中间分支"| N2
  N2 -.->|"③ 找到叶子，拿到行地址"| L1

100 万行数据，树的高度通常只有 3 层——意味着最多读 3 个节点就能定位，而不是读 100 万行。这就是快 1000 倍的原因。

聚簇索引：为什么主键要用自增整数

InnoDB 有个特殊设计：数据行本身就存在主键索引的叶子节点里。这叫聚簇索引（Clustered Index），意味着主键索引不是「指向数据的目录」，它就是数据本身。

其他索引（叫二次索引 / 辅助索引）的叶子里存的是主键值，所以用二次索引查非索引列时要走两步：

flowchart LR
  Q["WHERE user_id = 1001
要查 amount"] --> S["① 查 idx_user_status
找到主键 id = 88"]
  S --> P["② 拿 id=88 回主键索引
取出整行数据"]
  P --> R["拿到 amount"]
  S -.->|"这一步叫回表"| P

理解了这个结构，前面几条建议的原因就都清楚了：

  • 主键必须自增：新数据总是追加在索引树末尾。如果用 UUID 这种随机值，新数据会插到树的中间，导致页分裂（把已排好的页劈开腾位置），写入变慢、磁盘空间浪费
  • 主键要短：每个二次索引都存了一份主键值，主键从 8 字节的 BIGINT 换成 36 字节的 UUID 字符串，所有索引都跟着膨胀 4 倍

组合索引与「最左前缀」

组合索引是把多列合成一个索引，比如 KEY idx_user_status (user_id, status)。理解它的关键类比是电话簿按「姓，名」排序：

  • 知道姓「张」→ 能快速定位（用到索引）
  • 知道姓「张」名「三」→ 能更精确定位（完整用到索引）
  • 只知道名「三」→ 没用，只能全本翻（用不到索引）
flowchart LR
  I["组合索引 (user_id, status)"] --> A["WHERE user_id=1001
✅ 用到"]
  I --> B["WHERE user_id=1001 AND status=1
✅ 完整用到"]
  I --> C["WHERE status=1
❌ 跳过了第一列，用不到"]
  I --> D["WHERE status=1 AND user_id=1001
✅ 用到（顺序无关，优化器会调整）"]

这叫最左前缀原则：组合索引只能从最左边的列开始连续使用。所以 (user_id, status) 这一个索引，实际上顶了 (user_id) 和 (user_id, status) 两个索引的用途——但顶不了 (status)。

推论：建组合索引时，把区分度高、最常单独查询的列放前面。 如果业务上确实经常单独按 status 查，那就得再建一个 (status) 索引。

判断标准：多个写操作在业务上必须同时成立。

场景 要不要事务

单条 UPDATE/INSERT 不需要，单条语句本身就是原子的

写数据库 + 调第三方 HTTP 接口 不能放一个事务里，见下文

最后一条是新手最容易犯的错误：

事务要尽可能短。事务期间会持有锁，时间越长，其他请求排队越久，死锁概率越高。

ACID：事务的四个承诺

这是面试常问的概念，但理解它对写代码确实有帮助：

特性 含义 对应上面的例子
A 原子性 Atomicity 要么全做，要么全不做 不会出现只扣款没入账
C 一致性 Consistency 事务前后数据都满足业务规则 转账前后总额不变
I 隔离性 Isolation 并发事务互不干扰 别人查不到我未提交的中间状态

其中隔离性最微妙，因为它不是「有或没有」，而是有强度分级——这就是下一节的隔离级别。

3.10 隔离级别：并发时能看到别人的什么

使用背景：线上永远是多个请求同时跑。当两个事务同时操作同一批数据，A 事务能不能看到 B 事务的修改？看到多少？这就是隔离级别在规定的事情。

先认识三个会出问题的现象。假设 A、B 两个事务并发：

① 脏读：读到了别人还没提交、后来又回滚了的数据

sequenceDiagram
  participant A as 事务 A
  participant DB as 数据库
  participant B as 事务 B
  B->>DB: 把库存改成 0（未提交）
  A->>DB: 查库存
  DB-->>A: 返回 0
  Note over A: A 据此判断"卖光了"
拒绝了用户下单
  B->>DB: ROLLBACK（改回 100）
  Note over A,DB: A 读到的 0 从未真实存在过
白白拒绝了一笔订单

② 不可重复读：同一个事务里，两次读同一行，结果不一样（因为别人在中间改了并提交了）

③ 幻读：同一个事务里，两次读同一个范围，第二次多出了几行（别人插入了新数据）

四个隔离级别，就是对这三个现象的不同容忍度：

隔离级别 脏读 不可重复读 幻读 实际用途
READ UNCOMMITTED 会 会 会 基本没人用
READ COMMITTED 不会 会 会 PostgreSQL/Oracle 默认；高并发场景锁冲突少
REPEATABLE READ 不会 不会 基本不会 MySQL 默认，不用改
SERIALIZABLE 不会 不会 不会 完全串行，性能太差

  RU["READ UNCOMMITTED
啥都能看到"] --> RC["READ COMMITTED

  RC --> RR["REPEATABLE READ

  RR --> S["SERIALIZABLE

  RU -.->|"隔离性越来越强"| S
  S -.->|"并发性能越来越差"| RU

结论先说：MySQL 默认的 REPEATABLE READ 对绝大多数业务是合适的，不要去改它。 知道它的存在，主要是为了理解下面这个坑。

RR 级别下最容易踩的坑：读到的是「快照」

在 RR 级别下，事务第一次读取时会给数据「拍个快照」，之后整个事务里读到的都是这个快照——即使别人已经改了并提交了，你也看不到。

问题在于「读出来 → 在代码里计算 → 写回去」这个模式：读和写之间有时间差，别人可能已经改了。两种正确解法：

解法一：原子更新（推荐，无锁，性能最好）

4.2 先搞懂：连接、连接池、什么时候用哪个

这一节是新手最容易迷糊的地方，先把概念理清再看代码。

什么是「连接」

连接（Connection）就是你的 Node 进程和 MySQL 服务器之间的一条 TCP 通道。 每次执行 SQL，都是通过某条连接把语句发过去、把结果读回来。

建立一条连接不便宜，要走完整的握手流程：

sequenceDiagram
  participant N as Node.js
  participant M as MySQL
  N->>M: ① TCP 三次握手
  M-->>N: ② 返回握手包（版本、盐值）
  N->>M: ③ 发送用户名 + 加密密码
  M->>M: ④ 校验权限、分配线程和内存
  M-->>N: ⑤ 认证通过
  N->>M: ⑥ 终于可以发 SQL 了
  Note over N,M: 整套流程通常要几十毫秒
而一条简单查询只要 1~2 毫秒

也就是说，如果每个 HTTP 请求都新建一条连接、用完就关，光是建连的开销就是查询本身的十几倍。而且 MySQL 侧每条连接都要分配线程和内存，频繁创建销毁对服务器也是负担。

连接池解决什么问题

连接池（Pool）就是预先建好一批连接放着复用。 请求来了从池里「借」一条，用完「还」回去，不真正关闭：

    R4["请求 4
（池满了，排队等）"] -.-> P
    P["连接池

  P ==>|"连接 A（已借出）"| DB[("MySQL")]
  P ==>|"连接 B（已借出）"| DB
  P ==>|"连接 C（已借出）"| DB

对比一下：

每次新建连接 连接池
每个请求的建连开销 几十毫秒 0（复用现成的）
MySQL 侧压力 频繁创建销毁线程 稳定的少量长连接
并发失控风险 1000 个请求 = 1000 条连接，直接打满 MySQL 最多 connectionLimit 条，多的排队

结论：生产代码永远用连接池，不要用 createConnection。 连接池顺带解决了「限流」问题——它天然限制了你的应用最多能同时压给数据库多少个查询。

pool 和 connection 分别什么时候用

mysql2 里有三个层级的 API，用错会出 bug（尤其是事务）：

写法 是什么 什么时候用
pool.execute(sql) 自动借一条连接、执行、自动归还 默认用这个，单条独立的查询
pool.getConnection() 手动借一条连接，自己负责归还 需要多条 SQL 跑在同一条连接上时：事务、临时变量、FOR UPDATE
mysql.createConnection() 直接建一条独立连接，不走池 一次性脚本、数据迁移工具、单元测试

关键在于理解一件事：pool.execute() 每次调用可能用的是不同的连接。

事务、锁、会话变量都是绑定在单条连接上的状态，所以必须先 getConnection() 拿到一条固定的连接，全程用它：

release() 必须写在 finally 里。 如果写在 try 的末尾，中途抛异常就不会执行，那条连接就永久「借出去不还」了。借光之后所有请求都会卡在等连接，表现为「接口全部超时」，而 MySQL 那边看起来毫无压力——这是很难排查的一类线上事故。

queueLimit: 0（无限排队）的风险是：数据库变慢时请求会无限堆积，内存涨、响应越来越慢，最后整个进程崩掉。生产环境如果有网关层超时保护，设个 queueLimit（比如 connectionLimit × 10）能更早暴露问题。

流量有波峰波谷时用得上。高峰期池子涨到 20 条连接，低谷期只需要 2 条——剩下 18 条空着占用 MySQL 资源：

设 maxIdle 等于 connectionLimit（默认行为）意味着连接建立后就一直留着，适合流量平稳的服务——省去了重新建连的开销。流量波动大的服务才需要调小。

enableKeepAlive：云环境的必备项

这个参数解决一类特别诡异的 bug： 应用跑一段时间后，第一个请求总是失败，重试就好了。

原因是云上的负载均衡器、NAT 网关通常会切断空闲超过 5~10 分钟的 TCP 连接，但不会通知两端。你的连接池以为连接还活着，实际上已经断了，直到真正发 SQL 时才报 ECONNRESET 或 PROTOCOL_CONNECTION_LOST。

enableKeepAlive: true 让驱动定期发探测包，保持连接活跃，中间设备就不会认为它空闲。部署在云上就把它打开，本地开发无所谓。

timezone 与 dateStrings：时间处理

时区是 Node + MySQL 组合的高频坑：数据库存的 DATETIME 不带时区信息，驱动必须假设一个时区来转成 JS Date。如果驱动假设的和实际存的不一致，读出来就差几个小时。

统一约定「数据库存 UTC，timezone: 'Z'，展示时在前端转本地时区」，就不会有问题。

supportBigNumbers：不丢精度

JavaScript 的 Number 只能精确表示到 2^53（约 9007 万亿）。MySQL 的 BIGINT 上限远超这个数，直接转 Number 会静默丢精度：

自增主键涨到这个量级的项目不多，但雪花算法（Snowflake）生成的 ID 一开始就是 19 位，必然超范围。用雪花 ID 的项目必须开这个选项，或者干脆把 ID 列设计成 VARCHAR。

multipleStatements：保持 false

开启后一次能发多条用分号分隔的 SQL。它的危险在于：万一有 SQL 注入漏洞，攻击者原本只能篡改一条语句，现在可以追加 ; DROP TABLE users; --。 它把「注入」的破坏力放大了一个量级。真需要批量执行（比如跑迁移脚本），单独建一个连接临时开启，不要在业务池上开。

启动时探活

createPool 本身不会立刻建连接（是懒加载的），所以配置写错了不会马上报错。加一个启动探活能让「密码错了」「网络不通」这类问题在部署时就暴露，而不是上线后才发现。

6.1 单实例、多实例：什么时候需要不止一个 MySQL

选托管服务时值得先确认的几件事：是否支持按时间点恢复（PITR）、备份保留多久、主备切换时业务需要多久重连、有没有连接数上限（很多小规格实例只给几百个连接）。

6.5 安全加固清单

CREATE USER / GRANT / ALTER USER 这类语句会自动刷新权限缓存，不需要跟一句 FLUSH PRIVILEGES——只有直接改 mysql.* 系统表时才需要，而这本身就是应该避免的做法。

网络层同样重要：

  • 安全组只放行应用服务器所在网段的 3306，永远不要对 0.0.0.0/0 开放
  • 数据库放私有子网，通过跳板机或 VPN 访问
  • 应用连接串走 TLS：mysql://user:pass@host:3306/db?ssl={"rejectUnauthorized":true}
  • 备份加密存储，定期做恢复演练——没验证过的备份等于没有备份

七、分布式场景下的状态同步

这是最容易出事的一节。核心认知只有一句：MySQL 的复制默认是异步的，从库的数据永远可能比主库旧。所有分布式相关的坑，几乎都是从忽略这句话开始的。

7.1 复制原理

sequenceDiagram
  participant App as 应用
  participant P as 主库 Primary
  participant R as 从库 Replica

  App->>P: INSERT/UPDATE
  P->>P: 写 redo log + binlog
  P-->>App: 返回提交成功
  Note over App,P: 异步模式下这里就返回了
从库可能还没收到

  P->>R: IO 线程拉取 binlog
  R->>R: 写入 relay log
  R->>R: SQL 线程重放（可并行）
  Note over R: 此时从库才可见新数据

三种复制模式的取舍：

模式 主库何时返回 数据安全 性能 配置
异步复制 本地提交即返回 主库宕机可能丢数据 最好 默认
半同步复制 至少一个从库确认收到 binlog 基本不丢 增加一个 RTT rpl_semi_sync_source_enabled=1
组复制 MGR 多数节点达成共识 强一致 受最慢节点影响 InnoDB Cluster

注意半同步的超时降级：网络抖动导致从库确认超时后，主库会自动退回异步，此时的安全性承诺就消失了。监控 Rpl_semi_sync_source_status 才能发现这种静默降级。

7.5 分库分表

单表数据量超过约两千万行、或单库写入达到瓶颈时才考虑分片。先用尽索引优化、归档冷数据、读写分离这些手段，分片会引入跨库查询、分布式事务、扩容迁移等一系列复杂度。

分片键的选择决定了架构的成败：

  • 选高基数、查询必带的字段，多数业务是 user_id 或 tenant_id
  • 避免选自增 ID（写入热点集中）或时间（老分片只读、新分片打满）
  • 一个表只能有一个分片键，其他维度的查询需要建「索引表」或同步到 ES

需要跨分片的复杂查询时，中间件比手写路由省力得多：ShardingSphere-Proxy 对应用透明（伪装成 MySQL 协议），Vitess 适合超大规模，或者直接换成 TiDB / OceanBase 这类原生分布式数据库——它们把分片和分布式事务收进了存储层。

八、常见问题处理

8.1 Too many connections

真实原因通常不是 max_connections 太小，而是：

  • 连接没归还：忘了 conn.release()、事务抛异常没走 finally
  • 连接池配置乘法失控：20 个 Pod × connectionLimit: 50 = 1000 个连接
  • 慢查询堆积：查询变慢导致连接被长期占用，本质是性能问题

应急处理：

MySQL 预留了一个 SUPER 权限的连接名额，所以运维账号在连接打满时仍能登录——前提是应用账号没有 SUPER 权限。

8.2 慢查询定位与优化

examined_per_sent 这个比值最有诊断价值：扫了 10 万行只返回 10 行，说明索引不对。

优化顺序：先看 EXPLAIN 是否走索引 → 补合适的组合索引 → 减少回表（覆盖索引）→ 拆分复杂查询 → 最后才考虑加缓存或改架构。

8.3 深分页越翻越慢

游标分页的限制是不能跳页。如果产品一定要「跳到第 5000 页」，可以只对前 N 页提供精确分页、更深的页数走近似或引导用户加筛选条件。

8.4 死锁与锁等待

死锁的四条预防原则：

  1. 固定加锁顺序（多行更新前先按主键排序）
  2. 缩短事务：事务里绝不做 HTTP 调用、发消息、文件 IO
  3. 精确命中索引：更新条件走不到索引会锁住扫描过的所有行（RR 级别下还有间隙锁）
  4. 应用层重试：ER_LOCK_DEADLOCK 是可重试错误，MySQL 会自动回滚代价小的那个事务

死锁本身不是 bug，偶发死锁 + 自动重试是正常的；频繁死锁才需要改设计。

8.5 中文乱码

乱码只有四个可能出错的环节：服务端、库/表/列、连接、客户端。任意一环不是 utf8mb4 就会出问题。

Seconds_Behind_Source 只反映 SQL 线程的进度，网络阻塞时它可能显示 0 但实际已落后。更准的方式是用 pt-heartbeat 在主库写心跳、从库读时间差。

排查方向：

原因 表现 处理
从库单线程重放 主库多线程写，从库跟不上 开 replica_parallel_workers
大事务 延迟阶梯式跳增 拆成小批次（每批千行级）提交
从库缺索引 同一 SQL 在从库慢得多 保证主从表结构一致
从库硬件更差 长期存在稳定延迟 从库规格不应低于主库
无主键表 ROW 格式下每行更新都全表扫 所有表都必须有主键

最后一条值得强调：无主键的大表在 ROW 复制下能让从库延迟几个小时，这是最隐蔽也最容易踩的坑。

九、上生产前的检查清单

  • 所有表都有主键，且是自增整型
  • 字符集统一 utf8mb4，从服务端到连接串全链路一致
  • 金额用 DECIMAL，时间统一 UTC
  • 应用账号最小权限，不含 DROP/GRANT/SUPER
  • synchronize: false，表结构变更全部走迁移脚本
  • 连接池上限 × 实例数 < max_connections × 0.8
  • 连接归还写在 finally 里，事务不跨越网络调用
  • 慢查询日志开启，long_query_time ≤ 0.5s，有人定期看
  • 高频查询的 EXPLAIN 已确认走索引，无 ALL 和 filesort
  • 备份已配置并做过一次完整恢复演练
  • 3306 不对公网开放，连接走 TLS
  • 复制延迟、连接数、缓冲池命中率、磁盘使用率都有监控告警
  • 应用侧对 ER_LOCK_DEADLOCK、连接中断有重试和降级
  • 写后读场景已明确走主库还是容忍延迟

十、小结

MySQL 的复杂度不在语法，而在它的默认行为和你的业务假设之间的差距。索引不是加了就有效，事务不是包起来就安全，主从不是配好就一致。

按重要性排序，值得反复琢磨的三件事：

  1. 索引与执行计划——决定了单机能撑多少量，也是 90% 性能问题的答案
  2. 事务与锁——决定了数据对不对，出问题的代价远高于慢一点
  3. 复制的异步性——决定了分布式下的一致性边界，是架构设计的前提

工程上的建议是别急着上分布式。绝大多数业务在「单主 + 若干从库 + Redis 缓存 + 合理索引」这套组合下能撑到很大的规模；等到真的撞上单机瓶颈，再考虑分片或换原生分布式数据库，那时你也积累了足够的数据来做正确的决策。

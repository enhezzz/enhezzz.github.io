Vue + NestJS 构建智能 AI Agent 完全指南
发表于 2026-09-15| 更新于 2026-10-16|AI
字数总计: 8.4k|阅读时长: 38 分钟

AI Agent 不是简单的”问答机器人”，而是能够自主思考、使用工具、完成复杂任务的智能体。本文将带你用 Vue 3 + NestJS + LangChain 构建一个生产级 AI Agent 应用，从架构设计到完整代码实现，全程干货无废话。

我们会实现一个能够查天气、搜索网络、执行代码的智能助手，并对比 LangChain 和 Vercel AI SDK 两种方案的适用场景。

一、AI Agent 核心概念

什么是 AI Agent？

传统的 LLM 应用只是”对话界面”，而 AI Agent 是一个自主决策系统：

Agent 的四大核心能力

能力 说明 示例
推理（Reasoning） 理解任务，拆解步骤 “查北京天气”需要先获取位置，再调用天气API
工具使用（Tool Use） 调用外部工具/API 调用天气API、数据库查询、代码执行器
记忆（Memory） 记住上下文和历史 记住用户偏好、对话历史
规划（Planning） 制定多步骤计划 拆解”写一篇博客”为”调研→大纲→撰写→优化”

为什么选 LangChain 而非 Vercel AI SDK？

维度 LangChain Vercel AI SDK
Agent 能力 ✅ 完整的 Agent 框架，支持 ReAct、Plan-and-Execute 等 ⚠️ 基础 Tool 调用，Agent 能力有限
工具生态 ✅ 内置 100+ 工具，可自定义 ⚠️ 需手动实现工具逻辑
记忆管理 ✅ 多种记忆策略（对话、摘要、向量） ❌ 需自行实现
复杂度 较高，学习曲线陡 低，API 简洁
适用场景 复杂 Agent 任务 简单对话/流式生成

结论：如果只是做聊天机器人，Vercel AI SDK 足够；如果要构建能自主完成任务的 Agent，LangChain 是唯一选择。

工具定义、模型工具调用与结果回传分别发生在哪里？

这段代码的完整链路是：注册工具 → 将工具定义提供给 LLM → 接收模型的工具调用请求 → 执行工具 → 将结果加入下一次 LLM 请求 → 继续调用工具或生成最终回答。

从整个应用来看，这条链路由后端的 Agent 运行时协调；细分到代码，AgentService 负责创建组件、启动执行和转发输出，Agent 负责组织模型请求并解析决策，AgentExecutor 负责执行工具和控制循环，工具实例负责实际业务操作，LLM 负责选择工具、生成参数和根据结果作答。

阶段 本节代码中的入口 实际发生的事情
获取本地工具定义 createAgent() 中的 const tools = [...] 创建工具实例，取得工具名称、描述、输入 schema 和执行入口
将工具定义提供给模型 createOpenAIFunctionsAgent({ llm, tools, prompt }) 将工具定义绑定到模型调用配置，运行时随模型请求发送
接收模型的工具调用请求 agentExecutor.stream({ input: dto.message }) 启动的内部执行过程 模型适配器接收响应，Agent 的输出解析器将调用请求转换成 AgentAction
执行工具并取得结果 AgentExecutor 内部的工具调度过程 按 action.tool 找到工具实例，以 action.toolInput 调用工具，得到 observation
将工具结果传回模型 下一轮 Agent 执行时填充 agent_scratchpad 把模型先前的调用记录和工具结果组织成消息，再次请求 LLM
展示执行过程和回答 for await (const chunk of stream) 消费执行器输出，通过 subject.next(...) 转发给 Controller 和前端

这里的工具实例在每次 executeStream() 调用 createAgent() 时创建。构造函数中的日志没有创建工具；实际初始化发生在 const tools = [...] 处。

先区分 tools/list、tool_use 和工具调用动作

“工具列表”和“工具调用”是通用概念，但具体协议的字段名不同，不能把它们当成同一种网络消息。

名称 所属协议或组件 含义 本文中的对应关系
tools/list MCP MCP Client 向 MCP Server 查询可用工具定义 当前使用本地工具，未发出这个请求，由 const tools = [...] 提供工具集合
tools/call MCP MCP Client 请求 MCP Server 执行指定工具 当前由执行器直接调用本地工具实例
tool_use Claude API 模型响应中的工具调用内容块，包含名称和参数 对应“模型请求调用工具”这个阶段；本文没有使用 Claude
function_call 旧式 OpenAI Functions 接口 模型返回函数名称和参数 本文采用的旧式 Functions Agent 对应的调用格式
tool_calls OpenAI Chat Completions 工具调用接口 模型返回的工具调用列表 采用其他工具调用接口时可能看到的字段
AgentAction LangChain 框架解析后的调用动作，包含 tool、toolInput 等 执行器根据这个对象定位并执行工具

MCP 的方法名称是 tools/list 和 tools/call。如果“tool/use”指的是 Claude 的响应类型，其实际拼写是 tool_use。工具发现协议和模型工具调用协议处于不同链路：前者连接应用与工具服务器，后者连接应用与模型。MCP 工具协议、Claude 工具调用说明

本节使用 createOpenAIFunctionsAgent 和 AgentExecutor 这套旧式 API，安装命令没有锁定 LangChain 版本。这里按该 API 的设计解释执行链路；实际消息字段和流输出结构需要结合安装版本确认。

为什么 tools 要传两次？

第一次传入 tools 用于模型调用配置，模型看到工具的名称、描述和参数结构。第二次传入 tools 用于执行器的工具调度，后端保留 _call() 等实际实现。Prompt 中手写的“可用工具”列表只是说明文字，完整的机器可读工具定义由工具绑定过程提供。

Agent 产生 AgentAction 或 AgentFinish，执行器据此执行工具或结束；工具完成后，执行器保存调用动作和结果，再交给 Agent 组织下一轮模型请求。实现细节可参考 LangChain Agent 源码和执行器源码。链接指向主分支，具体 API 应以项目安装版本为准。

本节没有显式编写 sendToolResultToLLM()，结果回传由框架封装。关键连接点是 Prompt 中的占位符：

下一轮 Agent 执行时，框架将已保存的步骤转换成消息，填入 agent_scratchpad。以旧式 Functions 消息格式为例，发往模型的上下文可以理解为：

需要一并保留模型先前的调用请求和对应的工具结果，让模型知道结果属于哪次调用。chat_history 保存跨轮对话，agent_scratchpad 保存本次任务执行中的调用过程。工具返回后发起下一次模型请求，是应用或框架负责的步骤。OpenAI 官方 Function Calling 文档

for await 中看到的是执行过程输出

chunk.intermediateSteps 中的 step.action 表示调用了什么工具、传了什么参数，step.observation 表示该工具已经返回的结果。拿到 observation 时，工具已经执行完成，因此示例使用“工具执行完成”作为前端提示。

subject.next(...) 将信息转发给前端，工具结果交回 LLM 则由执行器的后续循环完成。若需要在工具开始时立即显示“正在调用”，应监听所用 LangChain 版本提供的工具开始事件或回调。

此外，agentExecutor.stream() 的执行步骤流与模型逐 token 文本流属于不同层级。此处 chunk.output 是执行器输出的回答，业务事件名 type: 'token' 并不能证明每个事件只包含一个模型 token。若需要逐 token 展示，应接收模型层文本流事件并转发。具体步骤字段也应以当前 LangChain 版本的流输出结构为准。

工具列表可以在初始化时获取并缓存，后续按需刷新；支持列表变更通知的服务器还可以通过 notifications/tools/list_changed 提醒客户端重新获取。无需每调用一次工具就执行一次 tools/list。MCP 工具协议

✅ 生产就绪：错误处理、会话管理、性能优化

关键要点

  1. Agent ≠ Chatbot：Agent 能够自主使用工具完成任务
  2. LangChain 适合复杂场景：多步推理、工具编排、记忆管理
  3. Vercel AI SDK 适合简单场景：轻量、易用、快速集成
  4. 流式输出是刚需：提升用户体验的关键
  5. 工具设计要谨慎：清晰的描述 + 安全的执行环境

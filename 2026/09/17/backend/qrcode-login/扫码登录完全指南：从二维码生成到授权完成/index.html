扫码登录完全指南：从二维码生成到授权完成
发表于 2026-09-17| 更新于 2026-09-17|Backend
字数总计: 17.3k|阅读时长: 78 分钟

扫码登录是一个很容易被低估的功能。表面上它只是”生成一张图片、等用户扫、然后跳转”，但真正动手实现时会发现，它本质上是一次跨设备的状态同步：二维码在 PC 浏览器上，登录态在手机 App 里，两个互不相识的客户端要通过服务端完成一次可信的身份传递。这里面藏着状态机设计、实时通知、防重放、防钓鱼一整套问题。

本文用一条主线讲清两件事：接入微信这类第三方扫码登录时发生了什么，以及自己从零实现一套扫码登录（含”扫码中”中间态）该怎么做。前端使用 Vue 3 + TypeScript，后端分别给出 Express 和 NestJS 两套完整实现，所有代码可直接落地。

一、扫码登录到底解决了什么问题

1.1 输入密码这件事在大屏上很别扭

PC 端登录的传统路径是”账号 + 密码 + 图形验证码 + 短信验证码”。它的问题不在于安全，而在于成本：

痛点 具体表现
输入成本高 用户要回忆密码，移动端习惯了指纹/面容后，密码记忆能力实际在退化
键盘记录风险 公共电脑、网吧、共享办公场景下，密码明文经过物理键盘
多因素太啰嗦 密码 + 短信码两步，转化率明显下降
账号体系割裂 新产品没有用户基础，注册流程本身就是流失点

扫码登录把”证明我是我”这件事整个搬到手机上完成。手机已经有可信登录态（长效 refresh token + 设备绑定 + 生物识别），PC 只需要接收这次授权的结果。用户的操作被压缩成两下：扫一下、点确认。

1.2 两种完全不同的”扫码登录”

这是最容易混淆的地方，一定要先分清楚，因为它们的工作量差了一个数量级：

区别在于状态机归谁维护：

  • 场景 A：二维码、”已扫码待确认”这个中间态、确认页 UI，全部由微信托管。你的服务端只在最后一步收到一个 code。工作量很小，但中间态的样式你控制不了。
  • 场景 B：ticket 的生成、状态流转、实时通知、过期回收，全部由你实现。”扫码中”是你自己的状态，UI 完全可控，还能同时对接自家 App、企业微信、钉钉，做成统一体验。

用户提到的”扫码确认中时页面有个扫码中的状态”，在场景 A 里是微信 iframe 内部渲染的（你看不到也改不了），在场景 B 里才是你要亲手实现的核心。本文两个场景都讲，重点在场景 B。

关键点：Web 端和 App 端从不直接通信。二维码只是一个把 ticket 从服务端搬运到 App 的”视觉信道”，所有信任都建立在服务端对 ticket 状态的独占写入上。

2.2 ticket 状态机

这是整个功能的骨架，先把它定下来，后面的接口设计就是自然推导：

stateDiagram-v2
    [*] --> PENDING: Web 申请二维码
    PENDING --> SCANNED: App 扫码上报
    PENDING --> EXPIRED: 超过有效期
    SCANNED --> CONFIRMED: 用户点击确认登录
    SCANNED --> CANCELED: 用户点击取消
    SCANNED --> EXPIRED: 超过有效期
    CONFIRMED --> CONSUMED: Web 换取会话成功
    CANCELED --> [*]
    EXPIRED --> [*]
    CONSUMED --> [*]

六个状态的语义和 Web 端 UI 的对应关系：

状态 含义 Web 端 UI
PENDING 已生成，等待扫码 正常展示二维码
SCANNED 已扫码，等待用户确认 二维码蒙层 + “扫码成功，请在手机上确认”
CONFIRMED 用户已确认，附带一次性凭证 “登录中…”
CONSUMED 凭证已兑换成会话 跳转到首页
CANCELED 用户在 App 上拒绝 “已取消，点击刷新重试”
EXPIRED 超时（Redis key 过期） 二维码置灰 + “已失效，点击刷新”

状态流转有三条铁律，违反任何一条都会出安全问题：

  1. 只能单向前进。SCANNED 不能回到 PENDING，CONFIRMED 不能被二次确认。用 Lua 脚本或 WATCH 保证 CAS 语义。
  2. 扫码阶段不下发任何凭证。SCANNED 时服务端只记录”是哪个用户扫的”，不生成 token。凭证只在 CONFIRMED 时产生。
  3. 凭证一次性消费。CONFIRMED → CONSUMED 必须是原子操作，防止同一个 ticket 被兑换两次会话。

三、二维码是如何生成的

3.1 二维码里到底装了什么

先破除一个常见误解：二维码不是图片格式，也不存储任何业务数据。它只是一段字符串的可视化编码。手机扫码得到的就是那段字符串，其他一切都发生在后续的 HTTP 请求里。

所以设计二维码内容的唯一问题是：这段字符串该写什么。

三种方案的差别在于被”错误的扫码器”扫到时的降级体验：

方案 自家 App 扫 微信 / 系统相机扫 评价
URL 识别 host + path，走登录流程 打开网页，可引导下载 App ✅ 体验最好
自定义 scheme 直接唤起 多数扫码器不识别，报错 ⚠️ 有兼容坑
纯 ticket 可用 显示一串乱码 ❌ 用户困惑

用 URL 方案时，App 端必须做域名白名单校验：只有 host 命中白名单才走登录流程，否则当普通链接打开。这是防钓鱼的第一道闸门，第八章会说明原因。

3.2 ticket 的生成要求

ticket 是这套机制里唯一的秘密，它的强度直接等于整个功能的安全下限：

Math.random() 不是密码学安全的随机源，V8 的实现基于 xorshift128+，观察到少量输出即可反推内部状态并预测后续值；时间戳更是完全可枚举。攻击者一旦能预测 ticket，就能在受害者扫码确认的瞬间抢先兑换会话。

三条硬性要求：

  1. 熵不低于 128 位，来自 crypto.randomBytes 或 crypto.randomUUID
  2. 短生命周期，2 到 5 分钟，靠 Redis TTL 自动回收
  3. URL 安全字符集，避免 base64 的 + / = 在 URL 里被转义出问题

四、场景 A：接入微信扫码登录

先讲第三方接入，它更常见，也能反过来帮你理解自建方案的设计取舍。

4.1 微信开放平台的两种扫码

微信的”扫码”有两套完全不同的能力，选错平台会白忙一场：

能力 平台 场景 拿到的用户标识
网站应用扫码登录 微信开放平台 open.weixin.qq.com PC 网站，微信 App 扫码 openid + unionid
公众号网页授权 微信公众平台 mp.weixin.qq.com 微信内置浏览器打开的 H5 openid

PC 端扫码登录要的是第一种，即微信开放平台的”网站应用”，需要企业资质认证并支付一次性审核费用。个人开发者做不了，这是硬门槛。

4.2 完整流程

微信扫码登录本质上就是 OAuth 2.0 授权码模式，只是把”跳转到授权页”换成了”展示二维码”：

    U->>App: 点击"确认登录"
    App->>WX: 确认授权
    WX->>W: 浏览器 302 重定向

注意最后几步：微信的 access_token 不是你的登录凭证。它只用来调微信的用户信息接口，拿到 unionid 之后就可以丢弃，或者加密存起来备用。你的网站会话必须用自己签发的 token 或 session，两者不要混淆，这是接入时最常见的错。

6.4 长轮询等待器

轮询是最简单的状态同步方式，但朴素轮询（每 2 秒发一次请求）在 5 分钟里会产生 150 次请求，绝大多数是无效的。改成长轮询：请求挂住最多 30 秒，状态一变就立即返回。

方式 延迟 服务端连接占用 实现复杂度 适用场景
朴素轮询 1 到 3 秒 低（请求短） ⭐ 最简单 快速验证、内部系统

8.2 组合式函数

几个容易忽略的实现细节：

  • onScopeDispose 而不是 onUnmounted：这样这个组合式函数在 effectScope 里也能正确清理，不限于组件上下文。
  • AbortController 必须有：长轮询请求挂起 30 秒，用户在这期间关掉弹窗，不 abort 的话请求会一直占着连接，回来还会写入已销毁组件的状态。
  • 本地倒计时先置过期：不依赖服务端返回 410 才切状态，因为长轮询可能正挂在那儿。
  • credentials: 'include'：exchange 这一步服务端要下发 httpOnly cookie，少了这个配置 cookie 不会被浏览器接受。

九、安全设计：扫码登录的攻击面

扫码登录看着简单，但它把”登录凭证的产生”和”登录凭证的使用”放在了两台设备上，中间靠一张任何人都能拍到的图片连接。这个特性带来了一批独有的攻击面。

9.1 二维码钓鱼：最现实的威胁

这是扫码登录最经典也最危险的攻击：

sequenceDiagram
    participant V as 受害者
    participant A as 攻击者

    A->>S: 1. 在自己电脑上打开登录页

    V->>V: 5. 用 App 扫码

    S-->>A: 7. 攻击者页面轮询到 CONFIRMED
    A->>S: 8. 兑换会话
    S-->>A: 9. 攻击者拿到受害者的登录态 ❌

问题的本质：服务端无法区分”用户在自己电脑前扫码”和”用户扫了别人电脑上的码”。技术上这两个请求完全一样。

问题 3 值得多说一句。如果不校验”确认者必须是扫码者”，会出现一种反向攻击：攻击者诱导受害者在受害者自己的电脑上打开登录页，拿到 ticket 后用攻击者的账号去确认。结果是受害者的浏览器登录了攻击者的账号——这叫会话嫁接（Session Fixation）。听起来无害，实际上很危险：受害者以为在自己账号下操作，往攻击者的账号里填了身份证、绑了银行卡。前面 assertScanner 那几行就是为了堵这个。

9.4 完整安全检查清单

accessToken 不放 localStorage 这条常被质疑。理由是 localStorage 对同源的任意脚本可读，一旦出现 XSS 就直接失窃；放在 Pinia 的内存里，配合 httpOnly refresh cookie 静默续期，刷新页面重新拿一次 accessToken 的成本很低，但把 XSS 的爆炸半径缩小了很多。

Redis Pub/Sub 天然跨实例，所以前面的实现直接就是多实例安全的。三个注意点：

  1. 订阅要用独立连接。Redis 连接进入订阅模式后不能再执行普通命令，必须 redis.duplicate()。前面的 subscriber / REDIS_SUBSCRIBER 就是为此。
  2. Pub/Sub 不保证投递。消息发出时若没有订阅者就直接丢弃。所以长轮询超时后必须回退到”再查一次 Redis 当前状态”，不能完全依赖消息。前面 finish() 里重新 getSession 就是这个兜底。
  3. Redis Cluster 下用 sharded Pub/Sub。普通 PUBLISH 在 Cluster 模式下会广播到所有节点，浪费带宽；Redis 7.0+ 用 SSUBSCRIBE / SPUBLISH 只在对应 slot 的节点间传播。

10.3 监控指标

扫码登录的漏斗特别值得埋点，因为每一步流失都指向具体问题：

几个关键比率和它们的含义：

指标 健康值 异常时的排查方向
扫码率 SCANNED / PENDING 60% 以上 偏低说明二维码不清晰、引导文案不明确，或用户找不到 App 扫码入口
确认率 CONFIRMED / SCANNED 90% 以上 偏低说明确认页信息让用户起疑，或按钮位置有问题

确认率是最能反映安全体验平衡的指标。 它太低说明确认页把用户吓住了，太高（接近 100%）反而要警惕：说明用户在无脑点确认，风险提示形同虚设，钓鱼攻击会畅通无阻。

10.4 常见问题速查

Q：二维码要不要自动刷新？

不要静默自动刷新。二维码在用户拿手机的过程中悄悄换掉，会导致扫到的是旧码然后报错，体验很差。正确做法是过期后置灰并显示”点击刷新”，把控制权交给用户。

Q：一张二维码能被多个账号扫吗？

不能。PENDING → SCANNED 是 CAS 流转，第一个扫的人锁定该 ticket，第二个人会收到 409。前端在 SCANNED 后加蒙层也是同一个意图。

Q：用户扫完码不确认也不取消，就切走了怎么办？

靠 TTL 兜底，5 分钟后 Redis key 消失，Web 端置为过期。不需要额外的定时任务清理。

Q：能不能跳过确认步骤，扫码即登录？

技术上可以（PENDING → CONFIRMED 一步到位），但强烈不建议。确认步骤是防钓鱼的唯一用户可感知的闸门，去掉它意味着任何人拍下你的二维码贴到任意地方，扫到的人就会不知不觉登进攻击者的浏览器。只有在纯内网、可信环境下才可以考虑简化。

Q：为什么不用 WebSocket？

扫码登录是单向推送，不需要双向通道。SSE 或长轮询已经够，而 WebSocket 会带来额外的握手成本、心跳维护和网关配置负担。如果项目里已经有一条 WebSocket 长连接，复用它当然是最省的。

十一、总结

11.1 核心要点

扫码登录的本质是用一张二维码把 ticket 从服务端搬到手机，再由手机上已有的可信登录态为这次 PC 登录背书。三个角色里，服务端是唯一的可信状态源，Web 端和 App 端从不直接通信。

环节 关键决策
二维码内容 装一个带 ticket 的 URL，App 校验 host 白名单
ticket 生成 crypto.randomBytes(16)，TTL 5 分钟
状态机 六态单向流转，全部走 Lua CAS 保证原子
凭证下发 扫码阶段不发凭证，CONFIRMED 时才生成 loginToken
会话兑换 ticket + loginToken 双因子，原子置 CONSUMED
状态同步 SSE 优先，长轮询兼容，都要有超时兜底
防钓鱼 确认页展示设备与地理位置，高风险要求二次验证

11.2 两种方案的选择

维度 接入微信（场景 A） 自建（场景 B）
开发量 1 到 2 天 1 到 2 周
资质门槛 需企业认证 + 审核费 无

对多数消费级产品，先接微信最快见效；有自家 App 且要把登录体验做成品牌一部分的，才值得自建。两者也常常并存——微信登录做拉新，自建扫码做老用户的快速登录。

11.3 上线检查清单

扫码登录真正的难点从来不是”怎么生成二维码”，而是在跨设备的状态同步里守住原子性，同时给用户留一个能看出异常的确认环节。前者靠 Lua 脚本和状态机设计，后者靠产品层的信息展示。两者缺一，功能都能跑，但都有洞。

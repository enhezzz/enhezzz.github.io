Web 安全完全指南：常见攻击原理与防范实战
发表于 2026-09-25| 更新于 2026-09-15|Security
字数总计: 19k|阅读时长: 86 分钟

安全问题的特殊之处在于：功能没做好，用户会抱怨；安全没做好，你可能完全不知道。一个未过滤的 v-html、一次字符串拼接的 SQL、一个忘记校验归属的 GET /api/orders/:id，在功能测试里全都是”通过”，直到某天数据出现在别人的数据库里。

本文按”原理 → 攻击链路 → 前端防范 → 后端防范”的顺序，梳理 Web 开发中最常见的十余类攻击。前端代码使用 Vue 3 + TypeScript，后端同时给出 Express 和 NestJS 两套实现，所有代码可直接落地到项目中。

一、建立安全的基本认知

1.1 攻击面全景

1.2 三条贯穿全文的原则

后面每一类攻击的防范手段，本质上都是这三条原则的具体应用：

原则 含义 典型违背
永不信任客户端输入 请求里的一切（body、query、header、cookie、文件名）都可被伪造 依赖前端校验、信任 Referer、信任前端传来的 role
数据与代码分离 用户数据永远作为”数据”传递，不参与代码/语句的拼接 拼接 SQL、eval、exec 拼接命令、v-html 渲染用户内容
默认拒绝，显式放行 权限、来源、字段、文件类型都用白名单而非黑名单 CORS 反射 Origin、上传只黑名单 .php、接口默认公开

1.3 纵深防御：不要指望单点防护

一个真实的 XSS 防护不是”加了转义就完事”，而是多层拦截，任意一层失效仍有后手：

注意第 ② 步：存储时不要提前转义。转义是输出阶段的、依赖上下文的操作，存储时转义会导致数据被反复转义（&amp;amp;），且无法适配不同输出场景（HTML / URL / JS / CSV）。

二、XSS 跨站脚本攻击

2.1 原理

XSS 的本质是：服务端或前端把用户提供的数据当作 HTML/JavaScript 代码执行了。浏览器无法区分”开发者写的脚本”和”从数据库里读出来的脚本”，只要它出现在 HTML 里，就会被执行。一旦脚本在受害者的页面上下文中运行，它就拥有该用户的全部权限：读取 localStorage 里的 token、以用户身份发起请求、篡改页面内容做钓鱼。

三、CSRF 跨站请求伪造

3.1 原理

CSRF 利用的是浏览器的一个默认行为：向某个域发请求时，会自动携带该域的 Cookie，不管请求是从哪个页面发起的。

所以如果你的转账接口只靠 Cookie 判断身份，攻击者只需要让已登录的用户访问一个恶意页面，页面里藏一个自动提交的表单，转账就完成了。用户全程只是”打开了一个网页”。

XSS 与 CSRF 的区别值得说清楚，很多人会混：

维度 XSS CSRF
攻击者能力 在你的页面执行脚本，能读取响应 只能”发起”请求，读不到响应内容
利用的信任 用户信任网站的内容 网站信任用户的浏览器
是否需要用户已登录 不一定 必须已登录
核心防御 输出编码 + CSP Token 校验 + SameSite

关键推论：XSS 可以完全绕过 CSRF 防护（脚本能读到页面里的 CSRF token）。所以修 CSRF 之前先确保没有 XSS。

机制 原理 局限
SameSite Cookie 浏览器在跨站请求中不发送 Cookie 依赖浏览器版本；子域名不算跨站

自定义请求头 跨域发自定义头会触发 CORS 预检 仅适用于 XHR/fetch，不防表单提交

3.4 后端防范（Express，双提交 Cookie 模式）

推荐 Double Submit Cookie 模式：token 同时放在 Cookie 和请求头里，服务端校验两者一致。它不需要服务端存储状态，适合 SPA。

关于 sameSite 的取值选择：

取值 跨站行为 适用场景
Strict 任何跨站请求都不带 Cookie，包括点击外链跳转 后台管理系统、支付类应用
Lax 跨站的顶级导航 GET 会带，POST 不带 大多数应用的推荐值
None 跨站始终携带，必须同时设置 Secure 确实需要跨站携带（如嵌入式第三方服务）

四、SQL 注入

4.5 额外的纵深防御

参数化解决了注入本身，但数据库层面还应该做限制，把”万一失手”的损失压到最小：

参数化查询 注入本身（根本解）
白名单映射表名/列名/排序 无法参数化的位置
数据库账号最小权限 注入成功后无法 DROP 表、读文件
关闭详细错误回显 报错注入无法从错误信息取数据
敏感字段加密存储 拖库后数据不可直接使用
慢查询与异常查询告警 及时发现盲注扫描行为

八、SSRF 服务端请求伪造

8.1 原理

只要你的服务端会”根据用户提供的 URL 去发请求”（图片转存、网页预览、Webhook 回调、导入远程文件），就存在 SSRF 风险。

危险之处在于：服务端通常位于内网，能访问外部访问不到的资源——数据库管理页、内部 API、以及云环境的元数据服务：

    participant API as 应用服务（公网）

    participant Cloud as 云资源

    Attacker->>API: 1. POST /api/fetch-image
url=http://169.254.169.254/latest/meta-data/...
    Note over API: 2. 未校验目标地址
    API->>Meta: 3. 服务端发起请求（内网可达）
    Meta-->>API: 4. 返回 IAM 临时凭证
    API-->>Attacker: 5. 凭证内容作为"图片抓取结果"回显
    Attacker->>Cloud: 6. 使用凭证直接操作云资源
    Note over Cloud: 7. 数据桶被读取/删除

十四、上线检查清单

输入与输出

  • 所有接口入参经过 schema 校验（类型、长度、格式、枚举）
  • 富文本经 DOMPurify 白名单净化，禁用裸 v-html
  • 数据库访问全部使用参数化查询，表名/列名走白名单映射
  • 系统命令调用使用 execFile / spawn，不启用 shell
  • 无 eval / new Function / $queryRawUnsafe（已由 ESLint 拦截）
  • 深合并逻辑过滤 __proto__ / constructor / prototype

认证与授权

  • 密码使用 Argon2id 或 bcrypt(cost ≥ 12) 存储
  • 登录失败文案统一，用户不存在时也执行等价哈希运算
  • 登录成功后重新生成会话标识
  • 每个涉及资源 ID 的接口都校验归属，返回 404 而非 403
  • 更新接口使用字段白名单，禁止整个 body 直接落库
  • userId 一律取自 token，不从 query / body 读取
  • 登录、注册、找回密码接口配置速率限制（IP + 账号双维度）

传输与浏览器策略

  • 全站 HTTPS，配置 HSTS（含 includeSubDomains）
  • 会话 Cookie 设置 HttpOnly + Secure + SameSite=Lax
  • CSRF token 双提交校验 + Origin 白名单
  • CSP 配置到位，frame-ancestors 防点击劫持
  • CORS 精确匹配 origin，不反射任意来源
  • X-Content-Type-Options: nosniff，接口 Content-Type 正确

文件与外部请求

  • 上传做扩展名白名单 + 魔数校验 + 图片重编码
  • 文件名由服务端生成（UUID），原始名仅作元数据
  • 上传目录与代码分离，用独立域名提供访问
  • 下载接口用 ID 查询，不接受路径参数拼接
  • 对外请求经 SSRF 校验（协议/端口/IP 白名单，禁重定向）

运维与可观测

  • 生产环境不返回堆栈，统一错误响应 + requestId
  • 关闭 x-powered-by 等指纹头，不输出 sourcemap
  • 环境变量启动时强制校验（密钥长度、必填项）
  • 数据库账号最小权限，敏感字段加密存储
  • pnpm audit 纳入 CI，锁定 lockfile
  • 关键操作记录审计日志（操作人、时间、IP、结果），日志中脱敏
  • 配置异常告警：401/403 激增、慢查询、大量 4xx

十五、小结

回顾全文，所有防范手段都可以归到三件事上：

第一，把数据当数据。 SQL 注入、命令注入、XSS 的根因完全一致——用户数据混进了代码/语句/标签的解析上下文。参数化查询、execFile 参数数组、模板自动转义，本质都是同一个动作：明确告诉解析器”这部分是数据，不要解释它”。

第二，每层都独立校验。 前端的表单校验、路由守卫、按钮显隐全是体验优化，攻击者根本不经过它们。服务端必须假设请求来自 curl，重新校验一切，包括那些前端”已经检查过”的字段。

第三，默认拒绝。 权限、来源、字段、文件类型、跳转地址，能用白名单就不要用黑名单。黑名单的问题不是”不够完善”，而是它永远不可能完善——你只能列举已知的攻击形式，而攻击者只需要找到一种你没想到的。

真正难的部分不是理解这些原理，而是让它们在团队里持续生效。可行的做法是把安全约束前移到工具链：ESLint 规则拦住 v-html 和 $queryRawUnsafe，ValidationPipe 的 whitelist 兜住批量赋值，全局 Guard 让归属校验成为默认行为，CI 里的 pnpm audit 卡住有漏洞的依赖。让不安全的写法通不过流水线，比要求每个人都记住二十条规则更可靠。

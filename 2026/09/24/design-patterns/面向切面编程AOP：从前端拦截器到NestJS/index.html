面向切面编程 AOP：从前端拦截器到 NestJS
发表于 2026-09-24| 更新于 2026-09-24|Design Patterns
字数总计: 2.9k|阅读时长: 9 分钟

假设你在做一个订单系统。createOrder() 负责创建订单，cancelOrder() 负责取消订单，getOrder() 负责查询订单。现在要给这些操作统一加上耗时日志、权限检查和异常上报。最直接的写法是在每个函数里各塞一遍代码；接口越多，重复越多，业务逻辑也越来越难读。

这正是面向切面编程（Aspect-Oriented Programming，AOP）要解决的问题：把散落在不同业务流程中的共同逻辑抽出来，在约定的执行位置统一接入。本文从这个使用背景出发，先看浏览器端的 Axios 拦截器和路由守卫，再看 NestJS 如何把同一思路放进服务端请求流程。

一、AOP 为什么出现

订单模块的主要工作是处理订单，但日志、鉴权、监控、缓存等能力会同时出现在订单、用户、支付等多个模块中。这类需求叫横切关注点：它们横跨多个业务边界，却不属于某一个业务对象的核心职责。

flowchart LR
  subgraph B["按业务划分的模块"]
    O["订单：创建 / 取消 / 查询"]
    U["用户：注册 / 修改 / 查询"]
    P["支付：发起 / 退款 / 查询"]
  end
  L["耗时日志"] -.-> O
  L -.-> U
  L -.-> P
  A["权限检查"] -.-> O
  A -.-> U
  A -.-> P
  E["异常上报"] -.-> O
  E -.-> U
  E -.-> P

如果在每个方法里复制这些代码，改一次日志格式就得改很多地方，还可能漏掉新接口。AOP 的做法是让业务方法专心处理订单，同时把日志等规则绑定到一组目标方法或请求阶段。

先记住四个词就够了：Spring 的 AOP 概念文档对这些术语有严格定义。

术语 通俗理解 订单系统里的例子
连接点（Join point） 程序运行中可以插入额外逻辑的位置 执行 createOrder() 时
切入点（Pointcut） 选中哪些连接点的规则 所有订单写操作
通知（Advice） 在选中的位置执行什么 调用前记录开始时间，结束后打印耗时
切面（Aspect） 把选中范围和附加行为组织起来 一套统一的耗时统计逻辑

把切面应用到目标流程的过程常称为织入（Weaving）。实现方式因工具而异：可能在编译时处理，也可能在运行时用代理或拦截链组合。写前端或 NestJS 时，通常无需自己实现织入机制；框架已经提供了接入点。

一个环绕式的切面可以想成这样：

flowchart LR
  A["进入：记录开始时间"] --> B["业务方法：创建订单"] --> C["退出：记录耗时"]
  B -->|"发生异常"| D["异常上报"]

这里最关键的区别是附加逻辑由统一入口接入，而不是散写在每个业务方法内部。它不会取代面向对象的模块划分；业务仍由订单、用户等模块承担。

二、前端哪里能看到 AOP 的思路

浏览器端并不一定使用传统 AOP 框架，但很多常见 API 都提供了“在统一位置处理多个调用”的能力。

位置 可以统一处理什么 接入范围
Axios 请求、响应拦截器 附加请求头、记录耗时、处理通用错误 使用该 Axios 实例发出的请求
Vue Router 导航守卫 登录态检查、页面访问限制、导航埋点 经过对应守卫的路由跳转
React 高阶组件或组件包装器 为一组页面加入埋点、权限提示等行为 被包装的组件

它们体现的是AOP 式的横切思路，不等于具备 Spring AOP 那样的切入点表达式和自动代理能力。单纯抽出一个工具函数、再让每个业务函数手动调用，也只是代码复用；统一接入到请求或导航生命周期，才更接近这里讨论的用法。

三、NestJS 中的 AOP 在哪里

NestJS 是运行在 Node.js 上的服务端框架。前端工程师做 BFF 或全栈项目时常会接触它。NestJS 官方明确说明，Interceptor（拦截器）的能力受到 AOP 启发：它可以在处理函数执行前后增加逻辑、转换结果或异常，甚至在特定条件下直接返回结果。

NestJS 还有一整套适合横切需求的组件。它们职责不同，不能全部当成同一种“拦截器”：

组件 典型用途 相对路由处理函数的位置
Middleware（中间件） 请求日志、给请求附加通用信息 路由处理前；此时尚不知道最终处理函数的元数据
Guard（守卫） 鉴权、角色与权限检查 决定请求能否进入后续流程
Interceptor（拦截器） 耗时统计、响应转换、缓存 可包裹处理函数的前后过程
Pipe（管道） 参数转换与校验 处理函数收到参数前
Exception Filter（异常过滤器） 统一处理未捕获异常并生成响应 出现未捕获异常时

正常情况下，NestJS 请求生命周期大致如下；异常会跳转到异常处理流程，过滤器不是每次请求都执行。

flowchart LR
  Q["HTTP 请求"] --> M["Middleware"] --> G["Guard"] --> I1["Interceptor
进入阶段"] --> P["Pipe"] --> C["Controller / Service"] --> I2["Interceptor
返回阶段"] --> R["HTTP 响应"]
  G -.->|"拒绝或抛错"| F["异常处理 / Filter"]
  P -.->|"抛错"| F
  C -.->|"抛错"| F
  I2 -.->|"未处理异常"| F
  F --> R

其中，Guard 适合回答“能不能访问”，Pipe 适合回答“参数是否有效”，Interceptor 适合回答“执行前后做什么”，Filter 适合回答“未处理异常如何返回”。一个接口可以同时用到它们，但每种组件的运行时机不同。

3.2 多个拦截器如何包裹业务

假设同时绑定日志和响应转换两个拦截器，它们会形成嵌套调用。NestJS 的入站顺序是全局 → 控制器 → 路由，返回时则路由 → 控制器 → 全局，类似层层打开再反向收起：

flowchart LR
  A["全局拦截器：进入"] --> B["控制器拦截器：进入"] --> C["路由拦截器：进入"] --> D["处理函数"] --> E["路由拦截器：返回"] --> F["控制器拦截器：返回"] --> G["全局拦截器：返回"]

这也解释了为什么响应转换、缓存、异常映射等功能适合放在拦截器里：它既能在调用前决定是否继续，也能处理返回的数据流。若拦截器不调用 next.handle()，处理函数就不会执行。具体能力和限制可参考 NestJS Interceptors 文档。

四、什么时候值得使用

适合抽成切面的，是规则一致、需要跨多个业务点复用、且有明确接入位置的逻辑，例如请求日志、性能监控、鉴权、参数校验和统一错误处理。某个订单状态转换的特殊业务规则只属于订单领域，仍应留在业务服务中。

设计时还要守住三条边界：

  1. 选择正确的阶段：NestJS 鉴权优先考虑 Guard，参数校验用 Pipe，处理函数前后逻辑用 Interceptor；不要让一个组件承担所有事情。
  2. 留意覆盖范围与顺序：Axios 实例、路由级绑定、控制器级绑定和全局绑定，作用范围不同；多个拦截器的顺序会改变结果。
  3. 保持行为可追踪：切面越多，调用链越不直观。为拦截器命名清楚，并让错误继续传递给负责处理它的层。

记住一句话：AOP 解决的是“同一类附加规则如何统一接入多个业务流程”。前端的请求拦截器、导航守卫，以及 NestJS 的 Guard、Interceptor、Pipe 和 Filter，都能从这个视角理解；但每种机制有自己的生命周期和边界，使用前先确定要拦截的到底是哪一步。

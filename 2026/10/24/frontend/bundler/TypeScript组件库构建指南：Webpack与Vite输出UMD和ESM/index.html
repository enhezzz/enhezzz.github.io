TypeScript 组件库构建指南：Webpack 与 Vite 输出 UMD 和 ESM
发表于 2026-10-24| 更新于 2026-10-27|前端
字数总计: 8.5k|阅读时长: 34 分钟

应用构建通常只需要一种运行方式，组件库却要考虑使用者如何加载：通过 <script> 引入时需要 UMD，通过现代打包器的 import 使用时需要 ESM，使用 require 的项目可能还需要独立的 CommonJS 产物，TypeScript 使用者则需要声明文件。本文用同一个 Vue 3 组件，分别给出 Webpack 和 Vite 的构建配置，并说明单入口、按组件导入、类型声明和 CSS 的发布方式。

示例采用 Vue 3 的 <script setup lang="ts">，不包含 JSX/TSX。重点是库的输出格式：Webpack 的 output.library.type 与 Vite 的 build.lib.formats，以及 Vue 作为外部依赖时两种格式各自的处理方式。

七、保留组件入口：ESM 与 CommonJS 分别构建

前面的 dist/index.mjs 是单入口构建：src/index.ts 虽然转导出各组件，但打包器会沿着导入关系把它们合进入口文件。源码里有 components/LightButton/index.ts，并不代表发布目录会自动出现同名的 JavaScript 文件。

构建方式 发布结果 适合的导入方式
单入口 一个 index.mjs 或 index.cjs import { LightButton } from 'light-ui-demo'
显式多入口 根入口与各组件入口各有文件；打包器还可能生成共享 chunk 同时支持包根入口和 light-ui-demo/LightButton
保留源模块 尽量按源码模块拆成文件，另有公共 chunk 或插件生成的模块 需要检查实际产物，并为公开的子路径指定稳定入口

CommonJS 也是同理：根入口转导出组件，只能决定根入口暴露什么 API；想发布可单独引用的组件文件，还要把组件子入口列入构建输入，并在 package.json 中导出相应子路径。下面的多入口配置独立于前面的 UMD 单入口配置；UMD 仍适合提供一个给浏览器直接加载的文件。

十、容易忽略的区别

  1. 格式选项不同。 Webpack 的 output.library.type 分别使用 'umd'、'module'、'commonjs2'；Vite 的 build.lib.formats 分别使用 'umd'、'es'、'cjs'。
  2. 外部依赖的映射不同。 UMD 必须明确浏览器全局变量 Vue；ESM 应保留对 vue 包的导入。仅将 Vue 写进 peerDependencies 不会自动把它从构建中排除。
  3. 声明文件需要单独生成。 Webpack 的 ts-loader.transpileOnly 和 Vite 的构建都不能替代 vue-tsc 对 .vue 组件的类型检查与声明生成。
  4. 多次构建不能互相清空产物。 Webpack 使用 output.clean: false，Vite 使用 emptyOutDir: false，并在整条构建命令开始时清理一次 dist。
  5. 入口数量与模块格式是两件事。 UMD、ESM、CommonJS 说明文件怎样被加载；单入口、多入口、模块保留决定文件如何拆分。根入口的转导出不会自动生成组件子入口产物。
  6. CSS 需要单独处理。 Webpack 用 CSS loader 和提取插件；Vite 库模式可通过 cssFileName 命名提取文件。把 CSS 加入包的导出，并标记其副作用。

十一、构建组件库时的考虑事项与设计原则

构建配置最终要兑现的是使用者写下的 import、require、CSS 导入和类型引用。先定义这些消费方式，再决定需要哪些产物；不必因为工具支持某种格式，就默认发布该格式。

  1. 先明确支持范围。 确认使用者需要现代打包器、Node/CommonJS、浏览器普通 <script> 中的哪些环境，以及最低运行版本。ESM 通常是现代应用的主要入口；仅在确有直接加载或旧项目需求时增加 UMD、CJS，并为每种格式提供可验证的消费示例。SSR 场景还应检查导入组件时是否立即访问 window、document。
  2. 把公开入口当作稳定 API。 决定包根入口和哪些组件子路径可被导入，再用 exports 明确映射到真实文件。源码目录、内部工具模块、构建生成的辅助 chunk 不应因为存在于发布包中就自动成为公开入口；调整已公开子路径也可能影响使用者。Node 的包入口文档说明了 exports 对子路径的封装行为。
  3. 区分按需入口与真正的模块拆分。 pkg/button 让使用者绕过根入口，但不保证组件内部依赖按源码文件拆开；需要 Element Plus 式模块目录时，才选择模块保留构建。无论哪种方案，都应检查根入口是否重复包含组件实现，并在实际消费方构建中检查未使用组件能否被移除。不要仅凭输出文件名判断是否实现了按需加载。
  4. 让依赖归属清楚。 Vue 这类需要与宿主应用共用的运行时放在 peerDependencies，同时在打包配置中设为 external；两项设置各管一件事。构建工具和编译器放在开发依赖；发布后的代码仍需自行加载的包应作为运行依赖。UMD 若将 Vue external，还要约定浏览器全局变量名和脚本加载顺序。
  5. 把样式作为发布契约设计。 决定是根入口加载全部样式、组件样式入口按需加载，还是由使用者显式导入 CSS；同时考虑基础样式、主题变量、字体或图片资源的路径与加载顺序。CSS 被提取到磁盘并不代表导入组件 JS 时会自动生效。sideEffects 需要保留有副作用的 CSS 和样式入口，避免消费方摇树优化时误删；参见 Webpack 的 CSS 与 tree shaking 示例。
  6. 让类型、JS 和包入口一一对应。 每个公开入口都应能找到可用声明文件，并分别验证 ESM 与 CJS 的类型解析。声明目录与源码目录保持相同相对结构只是第一步；若要支持严格 NodeNext，还要检查 .d.mts / .d.cts 的模块身份和声明内的相对导入扩展名。组件的 props、事件、插槽等类型也应与运行时 API 一致。
  7. 以发布包而非源码仓库验收。 完成构建后检查 npm pack --dry-run 列出的文件，再从打包结果安装到最小消费项目，分别测试根入口、组件子入口、import、require、CSS 和类型检查。构建脚本应先统一清理旧产物，再依次生成 JS、声明与样式，避免后一轮构建清空前一轮结果；这比只检查“构建命令成功”更能发现路径或发布文件遗漏。

设计组件本身时，也应保持组件入口、名称及 props／事件／插槽约定一致；把可复用行为留在组件内，把主题和全局配置作为明确的扩展点。这样构建出的多种格式才能对应同一套公共 API，而不是各自暴露不同的行为。

十二、sideEffects 如何影响组件库的摇树优化

package.json 的 sideEffects 是库作者给消费方打包器的提示：一个模块即使没有被使用的导出，执行它是否仍会产生需要保留的效果？导入 CSS、注册全局组件、安装 polyfill 或修改全局变量都属于这类效果。它不负责生成 CSS、不创建包子路径，也不会让 Node.js 自动加载样式。Webpack 将“根据 sideEffects 跳过整个模块及其依赖”与“分析模块中哪些导出未被使用”区分为两种优化；后者通常称为 usedExports。Webpack 的说明

package.json 写法 给打包器的含义 适用情况
"sideEffects": false 包内所有文件都可在导出未被使用时跳过执行 确认没有 CSS 导入、注册代码等执行副作用
"sideEffects": true 或不声明 保守地认为文件可能有副作用 尚未审查清楚副作用时
"sideEffects": ["**/*.css", ...] 仅列出的文件按有副作用处理，其余文件可被整模块跳过 JS 模块大多可摇树优化，但需保留样式等特定文件

例如第九节让使用者显式导入 light-ui-demo/style.css，这个 CSS 没有提供 JS 导出，但加载它会改变页面样式。若整个包标记为 sideEffects: false，生产构建可能把这次导入删掉，出现“组件正常渲染却没有样式”的结果。前面的 "sideEffects": ["**/*.css"] 正是为了保留这类 CSS 导入。它只保护已经被导入的 CSS，不会让只导入组件 JS 的使用者自动得到样式。

如果进一步提供 style/css.mjs、style/css.cjs 这样的纯样式 JS 入口，入口自身没有被使用的导出，只负责导入 CSS，那么还要把这些 JS 文件列入有副作用的范围。例如发布目录为 dist/esm 与 dist/cjs 时：

此时消费方显式导入样式入口，打包器才会继续处理它引用的 CSS。若仅保护 CSS，却把上层 style/css.mjs 当成无副作用模块整体跳过，打包器可能连它的 CSS 依赖也不再遍历。数组中的路径应匹配实际发布的文件，而不只是 src 路径；组件注册、polyfill 等入口也要按同一原则审查。Webpack 官方的组件库 CSS 示例展示了误设 false 时样式被删的情况。

最后用打包后的包做生产模式消费测试：分别只导入一个组件、只导入样式入口、从根入口导入组件，检查需要的 CSS 和初始化逻辑仍在，同时未使用的组件可以被移除。sideEffects 是对实际模块行为的声明；写得过于乐观会丢功能，写得过于保守会减弱整模块优化。

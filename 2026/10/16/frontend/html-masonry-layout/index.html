HTML 瀑布流布局实战：三种实现方案与大数据量优化
发表于 2026-10-16| 更新于 2026-10-23|前端
字数总计: 4k|阅读时长: 13 分钟

瀑布流把高度不同的卡片排成多列，尽量减少列内空白。图片社区、商品列表和作品集常用这种形式。看起来相似的瀑布流，可能使用完全不同的布局算法；选择方案时，先确定内容的阅读顺序、卡片高度何时确定和列表最多有多少项。

本文提供五个可直接打开的独立 HTML 演示。前三个展示布局，后两个展示大数据量优化；所有演示均不依赖框架或远程图片。

一、先选布局方案

方案 核心做法 适合场景 主要限制
CSS 多列 column-width 分栏，卡片避免跨栏拆开 展示型图片墙、文章卡片，追求实现简单 视觉阅读顺序通常先向下、再向右；不保证各列底部齐平
CSS Grid 动态跨行 小行高网格，按卡片实测高度设置 grid-row-end 需要 DOM 顺序从左到右、希望尽量用 CSS 管理列宽 需要测量和 ResizeObserver；行高有量化误差，不是真正的原生 masonry
JS 最短列定位 维护各列累计高度，逐项放到当前最短列 精确控制列间空隙、插入动画或复杂卡片 需要自己处理容器高度、响应式重排和动态内容高度

想快速上线静态作品墙，先试多列。若业务要求列表顺序从左到右，同时卡片高度不固定，可以考虑 Grid 动态跨行。需要按最短列精确放置，或要与虚拟滚动共用位置信息时，采用 JS 定位。CSS Grid 的普通自动排布会对齐同行轨道，单独写 grid-template-columns: repeat(...) 并不会得到真正的瀑布流。

1. CSS 多列：先弄懂列宽、列数与阅读顺序

先看演示实际使用的样式：

这几个属性各管一件事：

属性 含义 在演示中的效果
columns: 220px column-width 与 column-count 的简写；只给长度时，列宽的目标值为 220px，列数为 auto 容器变宽时可容纳更多列；220px 不是给卡片设置的固定 width
column-gap: 16px 列与列之间的水平间距 三列时一共有两个 16px 间距；它不控制卡片上下间距
break-inside: avoid 在分页或分栏的断开点，尽量避免从该元素内部断开 图片和标题尽量作为一张完整卡片移动到下一列；avoid 是避免断开，不是绝对保证
margin-bottom: 16px 同一列内卡片下方的外边距 控制上下卡片之间的视觉间距，与 column-gap 方向不同

为什么写了 220px，实际列宽却不是 220px？

column-width 是期望列宽。在容器有明确宽度、column-count: auto 且内容足够填满各列的常见情况下，可以用下面的方式估算。这里的 W 是多列容器的内容宽度，不是整个浏览器窗口宽度；g 是 column-gap，w 是期望列宽。

例如 W = 1000px、w = 220px、g = 16px：floor(1016 / 236) = 4 列，实际每列宽 (1000 - 3 × 16) / 4 = 238px。如果 W = 700px，则是 3 列，每列约 222.67px。当 W = 600px，只能放 2 列，每列 292px；容器甚至窄于 220px 时，单列也会缩到容器宽度。浏览器会把放不下新列的剩余宽度分给已有列，而不会在右边留下大块空白。

图中列宽按比例绘制；演示页顶部还会实时显示当前容器宽度、列数与卡片实际宽度。注意父元素的 max-width、padding、滚动条以及浏览器缩放都会影响 W，所以同一个 columns: 220px 在不同屏幕上出现不同列数是正常的。如果需要最多三列，可写 columns: 3 220px；如果要卡片永远精确 220px，则要另外设计剩余空间的分配方式。

多列布局还有一个容易误会的点：浏览器会根据内容分栏，默认尝试平衡各列高度；它不会逐张卡片去找“当前最短列”。对从左到右阅读的中文页面，视觉顺序一般是先沿第一列向下，再从第二列顶部继续，不是按一行从左到右排列：

图中的每列恰好放两张只是示意，实际分界点由卡片高度和浏览器分栏决定。图片墙适合这种排法；如果 1、2、3 必须横向相邻，就需要看下一种 Grid 方案。MDN 的多列布局说明也明确解释了剩余空间如何分给各列。

这里的空白是为了保住卡片完整性；break-inside: avoid 不会改变列间距，也不保证各列底部完全齐平。若单张卡片比整个列的可用高度还高，浏览器仍可能不得不断开。

2. Grid 动态跨行：从普通三列网格开始

如果之前没写过 Grid，先把它想成一张会自动增加行数的表格。容器负责规定“分几列、每列多宽、格子之间留多少空白”；直接子元素就是放进表格里的卡片。先不写瀑布流，只写最普通的三列：

repeat(3, 1fr) 只是 1fr 1fr 1fr 的简写。fr 可以理解为“分剩余空间的一份”：容器宽 700px，先扣掉两个 16px 列间距，剩下 668px 分三份，每列约 222.7px。默认先放第一行的 1、2、3，再放第二行的 4、5、6。这与 CSS 多列的“先向下再向右”不同。

普通 Grid 为什么还不是瀑布流？ 如图，第一行的 1 很高，2 和 3 很矮，但下一行仍要等第一行结束才开始，于是短卡片下方有空白。仅仅设置列数，不能让 5 自动顶到 2 的下方。

第一步：把“大行”换成很多“小刻度”

给容器加 grid-auto-rows: 8px。它的意思是：浏览器自动创建的每一小行高 8px。这里的“小行”是量高度的刻度，不是“每张卡片占一行”。gap: 16px 同时让相邻小行之间、相邻列之间各留 16px。

先用数字练习“占几行”。一张卡片如果占 1 条小行，可用高度是 8px；占 2 条，是 8 + 16 + 8 = 32px；占 3 条，是 8 + 16 + 8 + 16 + 8 = 56px。注意只有相邻两条小行之间才有间距，所以占 3 行只有 2 个间距。卡片越高，就需要占越多小行。

第二步：让每张卡片占够自己的高度

先看一个不用 JS 的固定例子：

span 5 就是“这张卡片从起点开始，占 5 条小行”。5 条 8px 小行加 4 个 16px 间距，一共 5 × 8 + 4 × 16 = 104px。如果卡片实际高 90px，104px 的位置足够装下它；只占 4 条时只有 4 × 8 + 3 × 16 = 80px，会装不下。

3. JS 最短列：精确计算位置

设每列当前底部为 columnHeights。对每张卡片，选高度最小的列，把卡片放到该列底部，再将卡片高度和间距计入这一列。所有卡片使用绝对定位，最后把容器高度设为最高列的高度。

演示把 DOM 写入、尺寸读取和位置写入分成几个阶段，避免在循环里反复“写样式 → 读高度”造成强制同步布局。真实图片页还应预留图片尺寸，并在图片载入、字体变化或容器宽度变化时重新布局。绝对定位改变的是视觉位置，不是 DOM/读屏顺序；涉及有序内容时要特别检查键盘导航。

二、数据量大时，优化的是不同的成本

瀑布流慢可能来自三处：一次拉取太多数据、同时解码太多图片、或者创建了太多 DOM。对应的手段不同：

  1. 分批请求或分页：服务端按游标返回下一批，首屏只渲染少量卡片。无限加载用 IntersectionObserver 观察列表底部的哨兵元素，提前一段距离请求下一页；同时要有“加载中、失败重试、没有更多”的状态，防止重复请求。
  2. 图片懒加载：给图片写明确的 width、height 或 aspect-ratio，预留空间；非首屏图片可设 loading="lazy"。需要自定义加载时机、占位图或优先级时，观察图片并在接近视口时设置 src。首屏关键图片不要一律懒加载。
  3. 减少绘制工作：content-visibility: auto 配合合理的 contain-intrinsic-size，可跳过视口外内容的部分渲染工作；它仍保留 DOM，因此不能代替虚拟滚动。
  4. 虚拟滚动：只挂载当前视口及前后缓冲区附近的卡片，滚走后移除。即使总数据达到数千项，DOM 数量仍可以保持在几十项级别。它要额外维护每项的位置、高度、窗口范围和滚动锚点。

打开分批加载与图片懒加载演示：离线演示用 SVG 数据地址模拟图片资源，真实项目应换为后端图片 URL，并配合缩略图、srcset、缓存与压缩格式。

打开 5000 项虚拟滚动演示：先根据已知卡片高度计算最短列位置，再按每列的可见区间创建卡片。页面会显示当前 DOM 节点数。示例使用可预测高度，方便把核心算法讲清楚。

图片高度未知时，虚拟滚动怎么办？

优先让接口返回图片原始宽高，结合当前列宽预估展示高度，并在数据模型中保存文本区域的估算高度。图片加载后若实测高度不同，更新该项及受影响的后续位置，同时维护当前可见卡片作为滚动锚点，避免页面突然跳动。若卡片高度变化频繁，虚拟列表实现会明显复杂；先用分页、懒加载和合理的每页大小，确认 DOM 确实是瓶颈，再引入虚拟滚动。

还有一个容易忽略的区别：loading="lazy" 只推迟资源加载，不会减少已创建的卡片 DOM；虚拟滚动会减少 DOM，但如果数据预取和图片加载策略不当，仍可能一次下载大量资源。虚拟列表中未挂载的卡片也无法被浏览器页面内查找直接命中，键盘导航和读屏体验需要单独设计；有明确检索需求时，应提供搜索或分页入口。

三、落地检查清单

  • 先确认视觉顺序、键盘顺序和读屏顺序能否接受。
  • 图片提供尺寸或宽高比，避免瀑布流反复位移。
  • 记录列宽、间距和测量公式，窗口变化时统一重排。
  • 对新增数据批量写 DOM，避免每插入一项就读取布局。
  • 测量真实瓶颈：网络耗时、图片解码、脚本布局耗时、DOM 数量和滚动帧率。
  • 无限滚动保留可到达的“加载更多”或分页入口，处理空状态与失败重试。

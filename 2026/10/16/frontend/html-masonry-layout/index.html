HTML 瀑布流布局实战：三种实现方案与大数据量优化
发表于 2026-10-16| 更新于 2026-10-16|前端
字数总计: 1.9k|阅读时长: 6 分钟

瀑布流把高度不同的卡片排成多列，尽量减少列内空白。图片社区、商品列表和作品集常用这种形式。看起来相似的瀑布流，可能使用完全不同的布局算法；选择方案时，先确定内容的阅读顺序、卡片高度何时确定和列表最多有多少项。

本文提供五个可直接打开的独立 HTML 演示。前三个展示布局，后两个展示大数据量优化；所有演示均不依赖框架或远程图片。

一、先选布局方案

方案 核心做法 适合场景 主要限制
CSS 多列 column-width 分栏，卡片避免跨栏拆开 展示型图片墙、文章卡片，追求实现简单 视觉阅读顺序通常先向下、再向右；不保证各列底部齐平
CSS Grid 动态跨行 小行高网格，按卡片实测高度设置 grid-row-end 需要 DOM 顺序从左到右、希望尽量用 CSS 管理列宽 需要测量和 ResizeObserver；行高有量化误差，不是真正的原生 masonry
JS 最短列定位 维护各列累计高度，逐项放到当前最短列 精确控制列间空隙、插入动画或复杂卡片 需要自己处理容器高度、响应式重排和动态内容高度

想快速上线静态作品墙，先试多列。若业务要求列表顺序从左到右，同时卡片高度不固定，可以考虑 Grid 动态跨行。需要按最短列精确放置，或要与虚拟滚动共用位置信息时，采用 JS 定位。CSS Grid 的普通自动排布会对齐同行轨道，单独写 grid-template-columns: repeat(...) 并不会得到真正的瀑布流。

1. CSS 多列：几行样式完成排版

浏览器根据容器宽度决定列数，卡片在同一列自上而下流动，再进入下一列。它适合顺序要求不严格的照片墙；如果编号 1、2、3 必须横向相邻，就不要把多列当成行优先网格。break-inside: avoid 防止卡片被拆到两列。列高度由浏览器排版决定，不能把它理解为“每次放进最短列”。

2. Grid 动态跨行：保留行优先 DOM 顺序

给卡片包一层网格项，测量内部内容的实际高度 h，再设置 grid-row-end: span Math.ceil((h + gap) / (rowHeight + gap))。当容器变窄、文字折行或者图片尺寸变化时，用 ResizeObserver 重新计算。公式中的 gap 必须与 CSS 一致，否则累计误差会让卡片重叠或留下明显空隙。

这种方案保留源码和键盘焦点的顺序，但视觉上可能有网格空洞；grid-auto-flow: dense 虽能回填空洞，却可能让视觉顺序偏离 DOM 顺序，因此演示没有启用。

3. JS 最短列：精确计算位置

设每列当前底部为 columnHeights。对每张卡片，选高度最小的列，把卡片放到该列底部，再将卡片高度和间距计入这一列。所有卡片使用绝对定位，最后把容器高度设为最高列的高度。

演示把 DOM 写入、尺寸读取和位置写入分成几个阶段，避免在循环里反复“写样式 → 读高度”造成强制同步布局。真实图片页还应预留图片尺寸，并在图片载入、字体变化或容器宽度变化时重新布局。绝对定位改变的是视觉位置，不是 DOM/读屏顺序；涉及有序内容时要特别检查键盘导航。

二、数据量大时，优化的是不同的成本

瀑布流慢可能来自三处：一次拉取太多数据、同时解码太多图片、或者创建了太多 DOM。对应的手段不同：

  1. 分批请求或分页：服务端按游标返回下一批，首屏只渲染少量卡片。无限加载用 IntersectionObserver 观察列表底部的哨兵元素，提前一段距离请求下一页；同时要有“加载中、失败重试、没有更多”的状态，防止重复请求。
  2. 图片懒加载：给图片写明确的 width、height 或 aspect-ratio，预留空间；非首屏图片可设 loading="lazy"。需要自定义加载时机、占位图或优先级时，观察图片并在接近视口时设置 src。首屏关键图片不要一律懒加载。
  3. 减少绘制工作：content-visibility: auto 配合合理的 contain-intrinsic-size，可跳过视口外内容的部分渲染工作；它仍保留 DOM，因此不能代替虚拟滚动。
  4. 虚拟滚动：只挂载当前视口及前后缓冲区附近的卡片，滚走后移除。即使总数据达到数千项，DOM 数量仍可以保持在几十项级别。它要额外维护每项的位置、高度、窗口范围和滚动锚点。

打开分批加载与图片懒加载演示：离线演示用 SVG 数据地址模拟图片资源，真实项目应换为后端图片 URL，并配合缩略图、srcset、缓存与压缩格式。

打开 5000 项虚拟滚动演示：先根据已知卡片高度计算最短列位置，再按每列的可见区间创建卡片。页面会显示当前 DOM 节点数。示例使用可预测高度，方便把核心算法讲清楚。

图片高度未知时，虚拟滚动怎么办？

优先让接口返回图片原始宽高，结合当前列宽预估展示高度，并在数据模型中保存文本区域的估算高度。图片加载后若实测高度不同，更新该项及受影响的后续位置，同时维护当前可见卡片作为滚动锚点，避免页面突然跳动。若卡片高度变化频繁，虚拟列表实现会明显复杂；先用分页、懒加载和合理的每页大小，确认 DOM 确实是瓶颈，再引入虚拟滚动。

还有一个容易忽略的区别：loading="lazy" 只推迟资源加载，不会减少已创建的卡片 DOM；虚拟滚动会减少 DOM，但如果数据预取和图片加载策略不当，仍可能一次下载大量资源。虚拟列表中未挂载的卡片也无法被浏览器页面内查找直接命中，键盘导航和读屏体验需要单独设计；有明确检索需求时，应提供搜索或分页入口。

三、落地检查清单

  • 先确认视觉顺序、键盘顺序和读屏顺序能否接受。
  • 图片提供尺寸或宽高比，避免瀑布流反复位移。
  • 记录列宽、间距和测量公式，窗口变化时统一重排。
  • 对新增数据批量写 DOM，避免每插入一项就读取布局。
  • 测量真实瓶颈：网络耗时、图片解码、脚本布局耗时、DOM 数量和滚动帧率。
  • 无限滚动保留可到达的“加载更多”或分页入口，处理空状态与失败重试。

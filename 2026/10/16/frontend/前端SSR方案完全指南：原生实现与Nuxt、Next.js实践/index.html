前端 SSR 方案完全指南：Vue、React 原生实现与 Nuxt、Next.js 实践
发表于 2026-10-16| 更新于 2026-10-23|前端
字数总计: 4.6k|阅读时长: 17 分钟

商品详情页需要搜索引擎读到商品信息，也希望用户打开页面时尽快看到标题和价格。纯客户端渲染可以实现这些功能，但首屏内容要等 JavaScript 下载、执行并取回数据后才能出现。服务端渲染（Server-Side Rendering，SSR）把生成初始 HTML 的工作移到服务器：浏览器先看到内容，再由客户端 JavaScript 接管交互。

本文以 Vue 和 React 为例，拆解原生 SSR 的实现链路，再看 Nuxt 和 Next.js 分别帮我们处理了什么，以及如何按页面需求选择方案。

一、先分清 SSR、CSR 和预渲染

方式 HTML 在何时生成 首次响应中的主要内容 常见场景
CSR（客户端渲染） 浏览器运行 JavaScript 后 应用容器和脚本引用 登录后的后台、强交互工具
SSR（请求时服务端渲染） 用户请求到来时 当前请求对应的页面内容 实时商品信息、个性化页面
SSG（静态生成） 构建或内容更新时 提前生成的页面内容 文档、更新频率低的文章

SSR 的核心流程是：

**Hydration（水合）**指客户端框架在已有的服务端 HTML 上建立组件状态和事件处理。用户“看到了按钮”不等于“按钮已经可点击”；交互仍取决于客户端脚本何时加载并完成水合。SSR 通常能改善内容出现的时机，也让爬虫更容易读取初始 HTML，但并不自动保证 Core Web Vitals 或搜索排名。服务器取数慢、HTML 无缓存、客户端包过大，都可能抵消收益。Vue 与 React 的官方文档分别解释了这一流程：Vue SSR、React hydrateRoot。

二、原生 SSR：自己串起服务端与客户端

这里的“原生”是直接调用 Vue / React 的渲染 API，由项目自己管理请求、路由、取数、HTML 模板、客户端入口和部署。实际项目仍需要 Vite 一类构建工具转换 .vue / JSX，并分别产出服务端和客户端代码；使用 Vite 不等于使用 SSR 应用框架。Vite SSR 指南给出了典型的双入口结构。

renderToString 太慢时，流式输出能改善什么

renderToString() 返回完整的 HTML 字符串。按前面的 await renderToString(app) 写法，响应主体要等整棵组件树渲染完才能发送：慢取数或慢渲染会增加首字节等待时间，也可能触发网关超时。Vue 的 renderToNodeStream() 返回 Node.js Readable，可把已生成的 HTML 逐步写入响应；但该 API 不支持 vue/server-renderer 的 ESM 构建，使用该构建时应改用 pipeToNodeWritable()。如果耗时操作发生在开始流式渲染之前，换 API 也无法提前送出页面内容。流式输出还要安排 HTML 头尾、初始状态脚本和客户端入口的先后顺序；首字节发出后，HTTP 状态码与响应头便不能再随意修改，中途出错需要另行处理。

浏览器不必等 </html> 到达才解析：收到前面的 HTML 后就可以增量构建 DOM，并可能先绘制标题或加载占位内容。但没有“收到多少字节就一定绘制”的标准门槛。首批内容要包含可见的 DOM，关键 CSS 不能一直阻塞绘制，也不能被同步脚本卡住；浏览器何时安排绘制仍取决于自身调度。先看到内容也不表示它已完成水合、可以交互。参见 浏览器关键渲染路径与 HTML 增量解析说明。

从 Node 写出一块，不保证浏览器立刻收到一块。以 Nginx 为例，proxy_buffering 默认开启，会从上游尽快读取并暂存响应；这不代表必然等完整响应结束才转发，但可能合并或延迟小块输出。需要逐块转发的 SSR 路径可以配置 proxy_buffering off;，或让上游返回 X-Accel-Buffering: no；后者在 Nginx 忽略该头时无效。CDN 等其他中间层也要按实际部署链路验证。参见 Nginx 的 proxy_buffering 文档。

传输格式也取决于浏览器连接使用的 HTTP 版本：HTTP/1.1 流式响应在长度未知时通常采用 Transfer-Encoding: chunked；HTTP/2 不允许这个头，而是用连续的 DATA 帧发送内容，并以 END_STREAM 标记结束。HTTP/2 仍可带 content-type 等普通响应头，没有专门的“流式头”。Node 到代理可以是 HTTP/1.1 chunked，而代理到浏览器是 HTTP/2 DATA 帧。RFC 9113规定了 HTTP/2 的消息格式。

适用场景：已有 Vue 应用只需给少量公共页面加 SSR，或团队需要完全控制 Node 服务、路由和缓存，并愿意维护双端构建链路。

三、框架方案：把通用 SSR 管线交给 Nuxt / Next.js

原生 SSR 给出渲染能力，应用框架进一步约定文件路由、数据加载、构建、资源注入和部署方式。框架并不是给 renderToString 加一个包装函数；它还要保证服务端与客户端拿到相同数据，并协调导航、缓存和错误处理。

3.1 Vue + Nuxt

Nuxt 默认采用通用渲染：请求到达后，在服务端运行 Vue 页面并返回 HTML；浏览器加载脚本后水合。页面可以用 useFetch / useAsyncData 获取数据，Nuxt 把服务端取到的数据放进页面 payload，供客户端水合复用，减少首次加载的重复请求。参见 Nuxt 渲染模式与数据获取教程。

这个示例假设项目已有 /api/articles/:id 接口。Nuxt 还支持用 routeRules 为不同路径选择预渲染、缓存或关闭 SSR，例如公开文章可使用缓存，而强依赖浏览器 API 的后台路由可单独使用客户端渲染。缓存公开内容时要明确更新时效；含用户身份信息的 HTML 不应直接共享缓存。

适用场景：Vue 内容站、电商前台、营销与产品页面并存的站点，特别是需要按路由组合 SSR、静态生成和客户端渲染时。代价是遵守 Nuxt 的目录和数据获取约定，并按其服务端运行环境部署。

3.2 React + Next.js App Router

Next.js App Router 默认把页面和布局作为 Server Components。服务端先生成 React Server Component Payload，并为首次访问生成 HTML；浏览器利用 payload 协调组件树，并水合需要交互的 Client Components。因此，Server Component 与“整页都在浏览器水合”不是同一个概念：标记 use client 的部分才承担客户端状态和事件。详见 Next.js Server and Client Components。

getArticle 代表项目自己的数据访问函数。页面主体留在服务端，按钮作为客户端边界；实际点赞还需调用接口并处理失败与服务端状态。Next.js 也支持预渲染、请求时渲染和基于 loading.tsx / Suspense 的流式输出；缓存行为受项目版本、配置和数据访问方式影响，不能把“使用了 Server Component”直接等同于“每个请求都会重新生成 HTML”。参见 Next.js 导航与渲染。

适用场景：React 多路由产品站、需要服务端数据访问及局部交互的应用，或希望用框架统一处理路由、流式渲染和部署的团队。代价是理解 Server / Client Component 边界及缓存语义；选择部署平台时还应确认所需的 Node 运行和流式传输能力。

四、怎么选：先按页面划分，再选实现方式

方案 你需要亲自处理 更合适的情况
Vue 原生 SSR 服务端路由、取数、双端构建、数据序列化、缓存 现有 Vue 项目仅少量页面需要 SSR，且已有后端体系
React 原生 SSR 同上；流式输出还需管理响应生命周期 现有 React 项目要增量改造，或需要精细控制 HTTP 输出
Nuxt 主要处理业务数据、路由规则和部署配置 新建或重构 Vue 多页面站点，渲染方式需要混用
Next.js 主要处理组件边界、取数缓存和部署配置 新建或重构 React 多页面站点，需要服务端组件与流式能力

一个实用判断顺序：

  1. 页面是否需要请求时的最新或个性化内容？ 如果不需要，优先评估 SSG；没有明显首屏或收录需求的登录后台，也可以保留 CSR。
  2. SSR 需求有多广？ 只有一两个已有页面，可以在原有服务中接入原生 SSR；大部分公开页面都需要服务端能力，框架通常能减少长期维护量。
  3. 团队能否承担服务端运行与缓存？ 请求时 SSR 会增加服务端工作量。先确定数据时效、缓存键和部署环境，再决定是否全站使用。

无论选哪一种方案，都要验证三件事：查看“页面源代码”或禁用 JavaScript 时是否真有期望的内容；检查服务端与客户端首帧数据是否一致；测量 TTFB、LCP 与交互时间，而不是只看页面是否能打开。随机数、当前时间、浏览器专有 API 和不合法的 HTML 嵌套，都可能造成 hydration mismatch。Vue 的水合问题说明和 React 的 hydrateRoot 注意事项都强调服务端与客户端首轮输出应一致。

五、总结

SSR 是一条“服务端生成首屏 HTML、浏览器继续接管交互”的渲染链路。Vue 的 renderToString / createSSRApp 和 React 的 renderToString / hydrateRoot 让我们理解并控制基础流程；Nuxt 与 Next.js 则把路由、数据传输、构建及多种渲染方式组织成完整应用方案。选择时应先看页面数据的实时性、公开内容范围和运维条件，再决定是局部接入原生 SSR，还是采用框架统一建设。
